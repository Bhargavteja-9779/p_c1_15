Abstract

Recently, the technological iteration of our method has played a significant role in promoting the automation of software engineering, especially in code generation. However, the increasing prevalence of Al-generated code also poses potential risks to code quality, security, intellectual property, and academic integrity. Although existing research has focused on AI-generated code detection, current methods have not paid sufficient attention to the Go programming language. Furthermore, most methods rely on a single model or homogeneous features, limiting the capacity to capture the features of AI-generated code in multiple dimensions, including semantics and syntax. To tackle these issues, this paper proposes a Dual-Encoder detector for AI-generated Go code. This method constructs a Dual-Encoder feature fusion framework, utilizing encoders from two code models, CodeBERT and UniXcoder, to extract complementary features from the semantic and syntactic dimensions of the code, thereby more effectively identifying Al-generated code. Extensive experimental results show that in terms of the F1 indicator, our method outperforms other baseline methods. Compared with the strongest baselines on each dataset, this model outperforms by approximately 7.6% in average F1 score on the Go language datasets generated by GPT-3.5-Turbo, CodeLlama-34B, and WizardCoder-34B. It also performs well on the dataset generated by WizardCoder-15B. This research helps identify AI-generated code in codebases, thereby supporting code review and security policy development. It can also enhance code traceability and the clarity of intellectual property, contributing to maintaining fairness and academic integrity in educational and research environments. Moreover, it also provides a new framework for detecting AI-generated code.

1 Introduction

Recently, code generated by Artificial Intelligence(AI) has been widely used in software development, but it has also brought about multiple problems related to code quality, security, and intellectual property (Liu et al. 2024). Previous research have shown that the code generated by artificial intelligence often has potential vulnerabilities, API misuse, logical flaws, and may also lead to code plagiarism (Guo et al. 2023) and copyright disputes (Yu et al. 2023). Especially in educational settings, the indiscriminate use of AI-generated code may affect students’ programming skills and reduce their academic integrity awareness (Prather et al. 2023). Due to the high cost and limited efficiency of manual code detection, the development of automated and high-precision AI-generated code detection methods has become an urgent need.

The need for detecting AI-generated code is widespread, but most existing research focuses on Python (Nguyen et al. 2024; Oedingen et al. 2024; Shi et al. 2024; Xu et al. 2025), with insufficient attention paid to Go, a key language in system programming. Go, with its concise syntax and superior performance, is preferred for building system-level software and cloud-native infrastructure like Docker and Kubernetes (Karri and Penugonda 2025). In these scenarios, code quality directly impacts system stability and security. Without adequate verification, introducing AI-generated code can lead to serious engineering and security incidents. This research aims to develop AI-generated code detection for Go, providing risk warnings and decision support for engineering practice. It helps teams identify and audit AI-generated content, assess AI usage and risks, and formulate review strategies. Additionally, it maintains traceability and intellectual property clarity for Go code assets, supporting open-source compliance and reducing legal risks. In education, it can serve as an auxiliary tool to promote fairness and academic integrity.

Generating correct and efficient Go code remains a challenge for our method. For instance, Buscemi (2023) found that across four generation tasks, ChatGPT’s success rate was 62.8% for Python but only 20% for Go. LSPAI (Go et al. 2025) evaluated unit test generation for industrial Go projects: GPT-4o achieved line coverage of just 1.16% and 0.20% on Logrus Sirupsen (2025) and Cobra Francia (2013), with effectiveness rates of 4.29% and 10.32%. DeepSeek-V3 reached 34.1% and 16.36% line coverage, with effectiveness rates of 21.43% and 15.65%. UniTSyn (He et al. 2024) evaluated six code generation models on the Go programming language test task, reporting an average accuracy of 36.6% and a pass rate of only 3.93%. Yin et al. (2025) built a Go evaluation dataset from eight real projects. When evaluating test code generation with three major models(CodeLlama, DeepSeek-Coder, and Magicoder), they obtained average line coverage rates of 18.8%, 19.5%, and 19.95%, respectively, and average compilation rates of 49.31%, 41.05%, and 41.41%. They also note that large language models often exhibit “illusion” in unit tests, generating calls to non-existent methods or using mismatched parameters due to limited understanding of project context.

The data above collectively demonstrates that current mainstream language models still have significant limitations in generating Go code, making it difficult to directly generate effective code suitable for continuous integration processes. Therefore, conducting research on AI-generated code detection for Go has significant practical implications. While existing AI-generated code detection methods have improved detection performance to some extent, they generally suffer from a key limitation: they rely on a single model (Nguyen et al. 2024; Xu et al. 2025; Openai 2023) or homogeneous feature representations (Oedingen et al. 2024; Mitchell et al. 2023; Idialu et al. 2024). Due to the singular representation dimension, existing methods struggle to fully capture the subtle differences in multiple dimensions such as syntactic regularity, structural complexity, and semantic consistency of AI-generated code, resulting in insufficient robustness of the detection mechanism when facing diverse code generation models.

To address the above issues, since different pre-trained models have different understandings of code due to their different model architectures and training objectives, we infer that if complementary code features can be extracted from two pre-trained models and effectively fused, it is expected to build a detection method with stronger discriminative power and higher generalization ability. Based on the above ideas, this paper proposes a dual encoder fusion detection method for the Go programming language. Specifically, we select two complementary pre-trained models: CodeBERT (Feng 2020), whose advantage lies in extracting semantic information of code. And UniXcoder (Guo et al. 2022), which focuses more on modeling the syntactic structure features of code. By fusing the code embedded features extracted by the encoders of the two models, our method can simultaneously utilize the semantic information and syntactic structure features of code to achieve a more accurate and stable detection effect on AI-generated Go code.

Our main contributions are summarized as follows:

  1. 1.

    Based on the dataset of Jianwang et al. (2024), we performed data filtering and cleaning to obtain a large-scale Go programming language AI-generated code detection dataset, covering more than 140,000 sets of comparative samples from four different models: GPT-3.5-Turbo, CodeLlama-34B, WizardCoder-34B and WizardCoder-15B, providing a data foundation for evaluating the generalization of the detection method.

  2. 2.

    We innovatively propose an AI-generated Go programming language code detection method based on a dual encoder feature fusion framework. By using the code semantic features extracted by CodeBERT and the code syntax structure features extracted by UniXcoder for linear transformation and interactive fusion, we significantly improve the detection performance of AI-generated Go programming language code and provide a new idea for building a higher-performance AI code detector.

  3. 3.

    We systematically evaluated three mainstream baseline methods and revealed the performance of different methods on multiple generative model datasets. The final experimental results showed that our method outperformed all baseline methods in the F1 index and reached the advanced level in the other four indicators.

  4. 4.

    We explored the essential differences between our method and the baseline methods in code embedding feature learning through t-SNE (Lvd and Hinton 2008) visualization qualitative analysis based on different category codes embedding vectors and quantitative analysis of mean cosine similarity, providing an interpretable basis for the model’s discriminative ability. 2 Related work

Recently, the rise of large language models in the field of code generation has not only been confined to theoretical discussions but has also become increasingly popular in practical development (Xu et al. 2022), how to effectively identify AI-generated code has become an important research topic. Although the detection technology for AI-generated text has become relatively mature, the research on the detection of AI-generated code is still in its infancy. The existing detection schemes can be roughly divided into three main types: metric-based, feature-based, and pre-trained model-based methods.

  1. 1)

    Metric based methods Metric based methods usually do not rely on additional training data, but rather use the statistical characteristics of the code itself under the pre-trained language model to determine its source. The core assumption of this type of method is that AI-generated code is usually more “typical” or “smoother” in probability distribution than human-written code. Early work mainly drew on the metric standards of text detection. The Entropy (Gehrmann et al. 2019) method assumes that AI-generated text has a higher conditional entropy and makes a judgment by calculating the average conditional entropy. For example, the Log-Likelihood method (Solaiman et al. 2019) uses a language model to calculate the average log-likelihood of all tokens in the code to determine its source, and the higher the value, the more likely the code is to be generated by AI. The Rank method (Gehrmann et al. 2019) and Log-Rank method (Ippolito et al. 2020) use the absolute rank and log rank of the token in the prediction distribution as the criteria for discrimination, respectively. The LRR method (Su et al. 2023) combines information from log-likelihood and log-rank. NPR (Su et al. 2023) and DetectGPT (Mitchell et al. 2023) improve detection performance by introducing a perturbation mechanism and comparing the probability statistical differences between the original sample and the perturbed generated sample. Among them, DetectGPT also introduces normalization processing, which further enhances the robustness of the method. For the structural characteristics of code, DetectCodeGPT (Shi et al. 2024) generates perturbed samples while ensuring that the semantics of the code are not destroyed (e.g., by inserting spaces and newlines), and then performs detection by comparing the difference between the original code and its perturbed version in the normalized perturbed log-rank score. Its core idea is that the stability of the statistical characteristics (such as the NPR score) of AI-generated code after being subjected to small perturbations is not as good as that of human-written code. These methods rely on shallow global features (such as log-likelihood, entropy, word rank, etc.), and the discriminative power of these global features will decrease significantly when encountering AI-generated code with highly similar semantic and syntactic structures.

  2. 2)

    Feature based methods The core of feature based methods is to distinguish between human and AI-generated code by identifying stylistic and structural patterns. This is achieved by using a curated set of manually defined features, which are then fed into conventional machine learning models for classification. Idialu et al. (2024) proposed a detection method based on code style metrics. This method extracts layout features, syntactic features and lexical features from the code, and integrates code complexity metrics to further enhance the discrimination ability of the features. On this basis, the XGBoost (Chen 2016) algorithm is used to construct a classification model to effectively combine these features, thereby achieving the distinction between the code generated by GPT-4 and the code written by humans. Bukhari et al. (2023) combined the lexical and syntactic features of C programs as input data and constructed detection models using multiple algorithms such as XGBoost and random forest. Oedingen et al. (2024) also adopted the idea of constructing feature representations and combining them with traditional supervised learning models to detect AI-generated code. Among them, the XGB+TF-IDF method, which combines TF-IDF (Robertson 2004) text embeddings with the XGBoost (Chen 2016) classifier, showed the best performance in this study. Although feature-based methods can achieve good results on specific datasets, their limitations lie in their heavy reliance on expert prior knowledge to design features, and the constructed feature engineering may not be well transferred to different programming languages or code paradigms. Furthermore, in the face of rapidly iterating code generation models, hand-crafted features may need constant adjustment, posing challenges to their generalization ability and long-term effectiveness.

  3. 3)

    Methods Based on Pre-trained Models

This type of methods directly leverages powerful pre-trained models and fine-tunes them for code detection tasks. They are designed to automatically learn deep semantic features of code, which helps avoid laborious manual feature engineering. By adapting existing pre-trained models, these approaches efficiently bridge general language understanding with specialized code analysis.

GPT-2 Detector (Openai 2023) is an early representative of this direction, achieving detection by fine-tuning the RoBERTa (Liu et al. 2019) model on text generated by GPT-2.

Nguyen et al. (2024) et al. proposed GPTSnifferer, which uses CodeBERT as the base model for fine-tuning to predict the source of the code.

The CodeGPTSensor proposed by Xu et al. (2025) uses UniXcode as a semantic encoder, embeds function code into hidden vectors, and introduces a contrastive learning framework to maximize the distance between hidden vectors of different categories of code, thereby enhancing the model’s feature discrimination ability and improving the classification performance of ChatGPT-generated code.

The above-mentioned methods based on pre-trained models only use a single model for feature extraction and training, and cannot capture the differences between AI-generated code and human-written code from multiple dimensions, resulting in insufficient detection capabilities in complex scenarios.

3 Methodology

In this section, we mainly introduce our method. The core of this method lies in designing a Dual-Encoder complementary feature fusion framework, which combines two complementary code pre-trained models to detect AI-generated code. The overall working framework of our method is shown in Fig. 1, and the specific workflow is shown in Algorithm 1.

In the feature processing stage, as shown in Section 3.1, our method first processes the input code into a tokenized sequence(Lines 2-4). Then, it uses the encoder of the CodeBERT pre-trained model as the code semantic encoder to perform encoding on the tokenized code sequence(Lines 6-8), focusing on capturing the semantic information of the code. Meanwhile, the encoder of the UniXcoder pre-trained model is used as the code syntax structure encoder to extract the code’s syntax structure, control flow patterns, and deep logical dependencies(lines 10-12).

In the feature fusion stage, as shown in Section 3.2, the two types of features undergo linear transformation and normalization operations through feature adapters(Lines 14-15) to map them to a shared representation space. Then, the two features are linearly concatenated and interactively fused through a fusion layer(Lines 16-17), resulting in a feature representation that combines code semantics and syntactic structure.

In the classification stage, as shown in Section 3.3, the fused features are input into a multilayer perceptron classifier(Line 18), which is gradually compressed into the class space through nonlinear transformation and normalization, and finally outputs the predicted probability.

During the training phase, as shown in Section 3.4, in addition to using the cross-entropy loss (Mannor et al. 2005) for supervised training of the classification task, we also introduced consistency constraints and contrastive learning with reference to CodeGPTSensor (Xu et al. 2025) to enhance the model’s robustness(lines 19-24).

In the subsequent sections of this article, the specific contents of each stage of this method will be elaborated in detail.

3.1 Feature processing stage

3.1.1 Source code tokenization

To facilitate model processing, the input source code string is first segmented, with the aim of converting the unstructured character stream into a sequence of sub-words that the model can operate on. The input code, after being tokenized as described in EL-CodeBert (Liu et al. 2022), is formulated as (1).

$$\begin{aligned} X=\{x_1,x_2,...,x_L\},\quad x_i\in \textit{V} \end{aligned}$$
(1)

Where V represents the sub-word vocabulary, and L represents the maximum sequence length. Each tag \(x_i\) is mapped to a vector representation \(e_i \in \mathbb {R}^d\) based on the vocabulary index of the pre-trained model, where d is the vector representation dimension of the pre-trained model. Thus, the embedded sequence E is obtained as the input of the model, as formulated in (2) based on EL-CodeBert (Liu et al. 2022).

$$\begin{aligned} E=\{e_1,e_2,...,e_L\},\quad E\in \mathbb {R}^{L\times d} \end{aligned}$$
(2)

During this process, the model can capture the context dependencies between words and model the semantic flow and lexical patterns of the code. Tokenized sequences, as a unified intermediate representation and a common interface for feature extraction of downstream models, also provide a unified representation basis for the deep integration of semantic information and structural information in source code.

3.1.2 Feature extraction

To obtain the feature vectors of the code from the preprocessed label sequence, we designed a dual-encoder framework, which is respectively used to extract the semantic information and syntactic structure information of the code.

(1)Semantic structure features are extracted by the CodeBERT (Hendrycks 2016) model. As shown in (3), the encoder outputs the context representation H for each position.

$$\begin{aligned} H=f_{\textrm{semantics}}(E),\quad H\in \mathbb {R}^{L\times d} \end{aligned}$$
(3)

Where \(f_{\text {semantics}}(\cdot )\) represents the feature extraction function for the code semantic encoder. To obtain the global semantic vector of the code, we follow the masked average pooling approach described in CodeBERT (Hendrycks 2016), which is expressed in (4).

$$\begin{aligned} S=\frac{\sum _{i=1}^Lm_i\cdot \textrm{h}_i}{\sum _{i=1}^Lm_i},\quad S{\in }\mathbb {R}^d\end{aligned}$$
(4)

Where \(h_i\) is the positional representation, \(m_i \in \{0,1\}\) is the mask indicator, and d is the feature dimension. The final result S is the global semantic representation.

(2)Syntactic structure features are extracted by the UniXcoder (Guo et al. 2022) model. This model first parses the original code into an Abstract Syntax Tree and then performs Transformer encoding on the tree structure to output feature representations. The Syntactic structure vector \(H^{AST}\) can be obtained from (5).

$$\begin{aligned} H^{AST}=f_{\textrm{AST}}(E),\quad H^{AST}\in \mathbb {R}^{N\times d} \end{aligned}$$
(5)

Where \(f_{\text {AST}}(\cdot )\) represents the feature extraction function for the syntax structure encoder, N is the number of AST nodes, and d is the feature dimension. According to (6), to obtain the global syntax structure vector, we also use masked average pooling as described in CodeBERT (Hendrycks 2016).

$$\begin{aligned} A=\frac{\sum _{j=1}^Nm_j^{AST}\cdot \textrm{h}_j^{AST}}{\sum _{j=1}^Nm_j^{AST}},\quad A\in \mathbb {R}^d \end{aligned}$$
(6)

Here, \(m_j^{\text {AST}}\) is the masking marker for the syntactic structure encoder, used to mask invalid nodes. \(h_i\) is the positional representation. The resulting A retains the global syntactic dependencies and structural discrimination information of the code and d is the feature dimension.

Through the above process, the text encoder and the structured encoder respectively generate the global semantic vector S and the global syntactic structure vector A of the code. These two vectors are complementary yet possess certain differences, laying the foundation for subsequent dimension adaptation and fusion.

3.1.3 Model adapter

Since semantic features S and syntactic structural features A originate from different models and are usually located in different feature spaces, we introduce a model adapter for each feature to achieve feature representation alignment. Essentially, it is a small feedforward neural network composed of a linear layer, a non-linear activation layer GELU (Hendrycks 2016), and a normalization layer LayerNorm (Ba and Kiros 2016). The subsequent (7) and (8) are defined similarly with reference to the formula in reference EL-CodeBert (Liu et al. 2022). For the representation S of the text encoder output, the adapter mapping structure is shown in (7).

$$\begin{aligned} \hat{S}=\textrm{LayerNorm}(\textrm{GELU}(W_sS+b_s)),\quad \hat{S}\in \mathbb {R}^d\end{aligned}$$
(7)

Where W is the weight matrix and b is the bias vector. Similarly, the AST features, after linear transformation and normalization, are mapped as (8).

$$\begin{aligned} \widehat{A}=\textrm{LayerNorm}(\textrm{GELU}(W_\textrm{a}A+b_\textrm{a})),\quad \widehat{A}\in \mathbb {R}^d\end{aligned}$$
(8)

After such processing, code features from different sources are projected into a common representation space, creating conditions for subsequent feature fusion.

3.2 Feature fusion stage

After obtaining the aligned code features, we achieve the fusion of semantic features and syntactic structure features through nonlinear interaction. Specifically, we first perform a linear phase on the two eigenvectors as described in (9).

$$\begin{aligned} Z=[\widehat{S};\widehat{A}],\quad Z\in \mathbb {R}^{2d}\end{aligned}$$
(9)

Subsequently, it is compressed into a unified representation through a fusion mechanism and a nonlinear layer, and robustness is improved by using a Dropout layer (Srivastava et al. 2014). The fusion feature F can be obtained from (10), following EL-CodeBert (Liu et al. 2022).

$$\begin{aligned} F={\text {LayerNorm}}({\text {Dropout}}({\text {GELU}}(W_f\mathrm {Z+}b_f))),\quad F{\in }\mathbb {R}^d\end{aligned}$$
(10)

This approach not only preserves semantic features but also maintains syntactic structural features, giving the final representation the advantages of both

3.3 Classification stage

In this study, we used a two-layer perceptron as the classification head. The fused features F are fed into the two-layer perceptron classifier to obtain logits. The prediction probability is then calculated using the softmax function. (11) to (13) are defined similarly to those in reference EL-CodeBert (Liu et al. 2022). The logits score is calculated as shown in (11).

$$\begin{aligned} \ell =W_2\textrm{GELU}(W_1F+b_1)+b_2\end{aligned}$$
(11)

Where \(\ell \) represents the unnormalized logits score, \(W_1\) and \(W_2\) are weight matrices, \(b_1\) and \(b_2\) are bias vectors, and \(\textrm{GELU}\) is the activation function.

The two-layer perceptron introduces a non-linear transformation through the \(\textrm{GELU}\) activation function in the intermediate layer, enabling it to learn more complex decision boundaries and effectively capture complex patterns in code representations. The first layer compresses the high-dimensional features \(F \in \mathbb {R}^{d}\) to a lower dimension \(F' \in \mathbb {R}^{d/2}\), achieving feature refinement and denoising; the second layer further maps \(F' \in \mathbb {R}^{d/2}\) to a binary classification space, forming a hierarchical feature processing flow.

The logits score \(\ell \) obtained after the feature vector passes through the two-layer perceptron is used to obtain the classification prediction probability using the softmax function as in (12).

$$\begin{aligned} p_i=\textrm{softmax}(\ell _i)=\frac{\exp (\ell _i)}{\sum _{i=1}^2\exp (\ell _i)}\end{aligned}$$
(12)

Where \(p_i\) represents the probability that a sample belongs to class i, \(\exp \) is the exponential function, and i represents the class. The final predicted class is determined by the maximum probability following (13).

$$\begin{aligned} \hat{y}=\arg \max _{i\in \{0,1\}}p_i\end{aligned}$$
(13)

Thus, the entire Dual-Encoder complementary feature fusion framework achieves a complete mapping from input code to classification decision.

3.4 Training phase

To enhance the robustness and generalization ability of the model, we introduce a multi-task loss optimization mechanism during training and define the loss functions in (14) to (17), following CodeGPTSensor (Xu et al. 2025).

First, we used cross-entropy loss for direct supervision of the classification task following (14).

$$\begin{aligned} L_{CE}=-\sum _{c=1}^Cy_c\mathrm {~log}\hat{y}_c\end{aligned}$$
(14)

Where \(y_c\) is the true distribution, \(\hat{y}_c\) is the predicted probability, and C is the number of classes.

Secondly, we introduce a consistency constraint to improve model stability by minimizing the difference in predicted distributions under different random perturbations. That is, for the same input, we obtain probability distributions p and q through two random forward propagations, and ensure the stability of the model under random perturbations by minimizing the symmetric KL divergence (Kullback and Leibler 1951), where \(D_{\text {KL}}\) is the KL divergence calculation function following (15).

$$\begin{aligned} L_{KL}=\frac{1}{2}\left( D_{KL}(p//q)+D_{KL}(q//p)\right) \end{aligned}$$
(15)

Finally, we incorporate contrastive learning regularization, which forces code features of different categories to separate in the representation space, further improving the model’s discriminative ability First, we used cross-entropy loss for direct supervision of the classification task following (16).

$$\begin{aligned} L_{CL}=\max \begin{pmatrix}0,\cos (\vec {u},\vec {v})\end{pmatrix}\end{aligned}$$
(16)

Where u and v are the representation vectors of positive and negative samples, and \(\cos \) is the cosine similarity function.

The final total loss function is shown in (17).

$$\begin{aligned} L=L_{CE}+\alpha L_{KL}+\beta L_{CL}\end{aligned}$$
(17)

Here, \(\alpha \) and \(\beta \) are weighting coefficients used to balance the contributions of each loss term. And the value of \(\alpha \) is 0.1 while the value of \(\beta \) is 0.2.

Through this joint optimization, the model can not only complete the classification task, but also exhibit stronger robustness and generalization in adversity resistance and class differentiation.

4 Experimental setup

This section will explain the construction method of the adopted dataset, introduce the baseline method and its implementation details, as well as the evaluation metrics used in the experiment.

4.1 Dataset construction

To support the experimental evaluation of the pre-trained model in distinguishing between human-written and AI-generated function-level Go programming language code, we preprocessed the Code-Related Content Dataset(CCD) released by Jianwang et al. (2024). The original CCD dataset contains various programming languages and task types. Here we pay special attention to the Doc2Code-LLM dataset because it contains parallel sample pairs of human-written code and AI-generated code generated by the same natural language description, and each data is only code generated based on the given text description, without natural language text. For sample sizes of all programming language datasets, please refer to Appendix A. We extracted all human-written and AI-generated Go programming language-related code as experimental samples. However, before directly using the extracted samples for model training, we found that inconsistencies in formatting could lead to the model learning biased and non-generalized features. Therefore, we performed the following data cleaning and standardization steps. This original dataset contains various programming languages and task types. After filtering and cleaning the data, a large-scale Go programming language AI-generated code detection dataset was obtained, covering more than 140,000 sets of comparison samples from four different models: GPT-3.5-Turbo, CodeLlama-34B, WizardCoder-34B, and WizardCoder-15B.

4.1.1 Data processing

Initial observations revealed a systematic difference in indentation between human-written and AI-generated samples in the original Doc2Code-LLM dataset: human-written code often used inconsistent indentation (such as single tabs or six or more spaces), while AI-generated code uniformly used a 4-space indentation pattern. This is because the Doc2Code-LLM dataset only collected the relevant code without standardizing indentation; therefore, the initial experimental results using the original dataset showed a classification accuracy close to 100%, as detailed in Appendix B. At this point, the model almost entirely relied on indentation differences as discriminative features, rather than learning the essential structure or semantic characteristics of the code. Since code indentation can be easily modified in real-world scenarios to circumvent detection, to eliminate the adverse effects of code indentation on model code classification, we uniformly converted the indentation of all code samples to 4 spaces. This ensures that the model can learn deeper features related to code structure and logic. For details on adjusting indentation, please refer to Appendix C.

4.1.2 Dataset partitioning

To investigate the transferability of existing methods for detecting AI-generated code across different AI models, this paper uses the Doc2Code-LLM dataset to partition the code generated by four models—GPT-3.5-Turbo, CodeLlama-34B, WizardCoder-34B, and WizardCoder-15B—into different datasets for comparative analysis, resulting in the following four datasets. 4.2 Evaluation baselines

To comprehensively evaluate the performance of the method we proposed, we reproduced three representative baseline detection methods in the experiment for comparison. To ensure the fairness of the comparison, all baseline methods were trained and tested on the same dataset.

4.2.1 Metric-based methods

Entropy (Gehrmann et al. 2019): This method assumes that AI-generated text has greater entropy than human text. A final judgment score is generated by averaging the entropy values of all characters, calculated by averaging the conditional entropy of each word given its context.

Log-Likelihood (Solaiman et al. 2019): This method uses a language model to output the mean log-likelihood of all characters in the text as a score. The higher the score, the higher the probability that the text was generated by AI.

Rank (Gehrmann et al. 2019): This method first infers the absolute rank of each word in a given context, and then averages these rank values to generate a final score. This score is negatively correlated with the probability of AI origin, i.e., the lower the score, the higher the probability that the content was generated by AI.

Log-Rank (Ippolito et al. 2020): This method performs a logarithmic transformation on word ranking values to calculate scores, and determines whether the text is generated by AI based on the scores. Its scores do not depend on the original absolute ranking data.

LRR (Su et al. 2023): This method uses the score obtained by dividing log-likelihood by log-rank as the basis for discrimination. Among them, log-likelihood rate is the average logarithmic probability of the token, representing the absolute confidence in the real token.

NPR (Su et al. 2023): This method generates perturbed samples by replacing some characters, and then calculates the ratio of the average log-rank of the perturbed samples to the log-rank of the original samples as the final score to serve as the basis for discrimination.

DetectGPT (Mitchell et al. 2023): This method first masks some characters in the original text, then uses a pre-trained model to complete the conditional data to obtain perturbed samples, and then calculates the difference between the logarithmic probability of the original samples and the average logarithmic probability of the perturbed samples. The score obtained after normalizing this difference is used as the basis for discrimination. DetectCodeGPT (Shi et al. 2024): This method perturbs the code by randomly inserting spaces and newlines without compromising its functionality. It then compares the difference in the normalized perturbation logarithm ranking scores of the original code and its multiple perturbation versions under the original model to detect the perturbation. If the NPR score of the original code drops significantly after perturbation, it is determined to be AI-generated.

4.2.2 Feature-based methods

XGB+TF-IDF: Oedingen et al. (2024) distinguished between human-generated and AI-generated code by constructing feature representations of the code and inputting them into traditional supervised learning models such as random forest and XGBoost for classification. We use the XGBoost and TF-IDF embedding combination method, which has the best performance in this paper, for evaluation.

4.2.3 Methods based on pre-trained models

GPT2-Detector-Detector (Openai 2023): GPT2-Detector-Detector is a GPT-2 text generation detection model obtained by OpenAI by fine-tuning the RoBERTa (Liu et al. 2019) model using the output of the 1.5B-parameter GPT-2 model.

GPTSnifferer (Nguyen et al. 2024): Nguyen et al. used the CodeBERT model as a classifier for training to predict whether the code was generated by AI.

CodeGPTSensor (Xu et al. 2025): Xu et al. used UniXcode as a semantic encoder, embedded the function source code into the hidden vector, and used a contrastive learning framework to maximize the distance between the hidden vectors of different categories of code to improve the model classification training effect. A model trained in this way can distinguish between code snippets written by humans and those generated by ChatGPT

4.4 Evaluation indicators

In the detection task of AI-generated code, for any given code, its classification result can be divided into four cases: if the code is actually generated by AI and correctly recognized by the model, it is called true positive (TP); If the code is actually written manually but is mistakenly identified as generated by AI, it is called a false positive (FP). If the code is actually generated by AI but is mistakenly identified as being written by humans, it is called a false negative (FN). If the code is actually written manually and is correctly determined, it is called true negative (TN). Based on the above classification, this section refers to the research method of CodeGPTSensor (Xu et al. 2025) and defines the evaluation indicators as shown in (18) to (23).

4.4.1 Accuracy

This indicator is expressed as the percentage of samples correctly identified by the model among the total samples following (18).

$$\begin{aligned} \text {Accuracy} = \frac{TP + TN}{TP + FP + TN + FN} \end{aligned}$$
(18)

This metric is used to measure the overall discriminative performance of a classifier across all samples.

4.4.2 Precision

As shown in (19), precision represents the proportion of samples that the model classifies as AI-generated but are actually AI-generated.

$$\begin{aligned} \text {Precision} = \frac{TP}{TP+FP} \end{aligned}$$
(19)

This metric reflects the reliability of the model in correctly identifying the positive class.

4.4.3 Recall

This indicator reflects the proportion of samples generated by AI that can be correctly recognized by the model following (20).

$$\begin{aligned} \text {Recall} = \frac{TP}{TP + FN} \end{aligned}$$
(20)

This metric is used to evaluate the model’s sensitivity and coverage of positive samples.

4.4.4 F1 score

F1 score is a comprehensive metric that can evaluate the performance of a model by comprehensively measuring accuracy and recall following (21).

$$\begin{aligned} F1 = 2 \times \frac{\text {Precision} \times \text {Recall}}{\text {Precision} + \text {Recall}} \end{aligned}$$
(21)

4.4.5 AUROC

The value of AUROC is defined as the area enclosed by the receiver operating characteristic curve (ROC curve) and the coordinate axes. The corresponding calculation is as shown in (22) and (23).

$$\begin{aligned} \text {TPR} = \frac{TP}{TP + FN} \end{aligned}$$
(22)
$$\begin{aligned} \text {FPR} = \frac{FP}{FP + TN} \end{aligned}$$
(23)

By adjusting the threshold of the classifier, we can obtain a series of (FPR, TPR) points to plot the AUROC curve.

6 Discussion

6.1 Mechanism analysis of performance differences

6.1.1 Performance and underlying mechanisms of different method types

As shown in Tables 2 to 5, the three baseline methods exhibit significant performance stratification and different generalization characteristics across the four datasets, which are closely related to their respective underlying mechanisms.

Metric-based methods perform the worst and are the most unstable. The fundamental reason for this is that these methods rely on shallow statistical features(such as log-likelihood, entropy, and word rank) output by the language model. As the parameter scale of the generative model increases, its output probability distribution tends to be consistent with human code, leading to a significant decrease in the discriminative power of these global statistical features. Simultaneously, these methods are highly sensitive to perturbation strategies(such as mask ratios and whitespace insertion rules), further exacerbating performance fluctuations. This phenomenon indicates that in the detection tasks of high-quality AI-generated code, it is difficult to achieve effective distinction merely by relying on probability and statistical features.

Feature-based methods exhibit significant performance fluctuations on different datasets: they perform exceptionally well on data generated by smaller generative models(such as WizardCoder-15B)(F1=0.999); However, on the data generated by GPT-3.5, the performance decreased significantly(F1=0.768). This difference reflects the limitation of such methods - their effectiveness is highly dependent on the token usage pattern of the generative model. Smaller models tend to reuse fixed token combinations and encoding patterns, making shallow statistical features such as TF-IDF have strong discriminative power; However, the code token distribution generated by generative models with larger parameter scales(such as GPT-3.5-Turbo) is more diverse and closer to the human coding style, resulting in a significant reduction in the discriminative ability of these features.

The overall performance of methods based on pre-trained models is superior to the first two types of methods, but the advantages of GPTSnifferer(based on CodeBERT) and CodeGPTSensor(based on UniXcoder) vary on different datasets. This difference reflects the inherent limitations of single-modal models: CodeBERT focuses on the semantic information of code and performs better on the CodeLlama dataset, where there are significant differences in vocabulary and contextual patterns; while UniXcoder excels at capturing syntactic structural features and has an advantage on datasets like GPT-3.5-Turbo, which are highly realistic at the semantic level but may contain implicit structural patterns. This indicates that when the discriminative information spans multiple dimensions, a single-dimensional model struggles to achieve comprehensive and stable detection.

6.1.2 The advantage mechanism of the our method method

Our method achieves excellent and stable performance on these four datasets, and its advantage stems from the following key design features:

The core of the method is the complementary feature fusion mechanism of the dual encoders. The semantic encoder(CodeBERT) focuses on capturing the functional semantics and contextual dependencies of the code, identifying feature patterns of AI models in naming, annotation, API calls, etc. The syntax structure encoder(UniXcoder) captures the subtle differences in syntactic structure and writing logic among different codes by analyzing the abstract syntax tree and data flow of the code. This dual-encoder design enables the model to comprehensively understand the feature differences between different source codes from a complementary perspective.

The feature adaptive fusion strategy aims to address the alignment and interaction challenges among different features. This strategy first uses a model adapter to map features from different sources to a shared representation space; Furthermore, through the fusion mechanism and nonlinear transformation, the deep interaction between semantic features and grammatical structure features is promoted, and ultimately a feature representation with stronger discriminability is generated.

6.3 Ablation experiment analysis

6.3.1 Contribution of individual encoders and necessity of feature complementarity

We evaluate the contribution of individual encoders by comparing the performance of Only_UniXcoder, Only_CodeBERT, and our complete method. The results show that, on most of the datasets we evaluated, the single-dimensional model is consistently less effective than the fusion model. Specifically, Only_CodeBERT achieves the lowest F1 scores on the GPT-3.5-Turbo, CodeLlama-34B, and WizardCoder-34B datasets, revealing the limitation of relying solely on semantic information when distinguishing high-quality generated code. In contrast, Only_UniXcoder significantly outperforms Only_CodeBERT on these three datasets, underscoring the importance of syntactic structure information. However, on the WizardCoder-15B dataset, Only_UniXcoder obtains an F1 score of 0.9098, which is considerably lower than that of Only_CodeBERT (0.9993), indicating that syntactic features alone are also insufficient for optimal detection. These observations highlight the necessity of complementing semantic and syntactic information. Notably, among the two single encoders, UniXcoder exhibits superior overall performance, achieving higher average F1 scores across the first three datasets and providing the most critical discriminative features for the fusion model. Its syntactic representations serve as the foundation for the complementary mechanism, confirming that UniXcoder contributes the most to the final detection capability in our method.

6.3.2 Discussion on fusion mechanism

To assess the impact of our fusion strategy, we compare the complete method with a variant that omits the feature fusion module (No_Fusion). The No_Fusion approach simply concatenates the features extracted by UniXcoder and CodeBERT without any further interaction. Across all four datasets, No_Fusion performs worse than the full model, demonstrating that naive concatenation cannot effectively align heterogeneous features or enable deep cross-modal collaboration. Our fusion mechanism, which maps features into a shared space and applies nonlinear transformations, generates a more discriminative unified representation and is key to achieving superior performance.

On the GPT-3.5-Turbo dataset, No_Fusion achieves an F1 score of 0.9205, while the full model reaches 0.9281—a modest gain of 0.82%. Meanwhile, Only_UniXcoder attains 0.9185 and Only_CodeBERT only 0.6094. This suggests that when semantic features are weakly discriminative, the benefits of complex fusion are limited, and simple concatenation can yield comparable results. However, on the CodeLlama-34B and WizardCoder-34B datasets, No_Fusion(0.9497 and 0.9523, respectively) performs slightly worse than Only_UniXcoder(0.9600 and 0.9556). This indicates that direct concatenation may be dominated by the stronger syntactic features from UniXcoder, failing to leverage the complementary information from CodeBERT, thereby hindering performance.

More importantly, on the WizardCoder-15B dataset, No_Fusion obtains an F1 score of 0.9193, Only_UniXcoder 0.9098, and Only_CodeBERT 0.9965, while the full model achieves an impressive 0.9994. This dramatic improvement shows that when both feature types are highly discriminative, our fusion mechanism effectively integrates and enhances them, surpassing both individual encoders and the simple concatenation baseline. The result underscores the pivotal role of UniXcoder: its syntactic features, when properly fused with semantic features, unlock the full potential of the model.

In summary, we draw the following conclusions:

  • When semantic features are weak, the gain from complex fusion is limited, and simple concatenation can achieve near-optimal performance.

  • However, when both feature types are strong, the proposed fusion mechanism significantly improves representation capability, with UniXcoder providing the dominant syntactic foundation that drives the overall performance gain.

  • Simple concatenation suffers from feature imbalance and lacks deep interaction, becoming a bottleneck especially when both features are important; the complete fusion method overcomes this by enabling synergistic enhancement, with UniXcoder contributing the most critical information.

6.4 Analysis of misclassified samples

To deeply explore the error patterns of the classifier, this study compares the code length differences between misclassified samples and correctly classified samples in each dataset. The aim is to reveal two aspects: first, which type of human-written code is most likely to be misjudged as AI-generated; second, what characteristics does AI-generated code possess to effectively evade detection. The specific analysis is based on the statistical average length of the code for each classification sample.

6.4.1 Human code misidentified as AI-generated feature analysis

As shown in Table 10, in the four datasets of GPT-3.5-Turbo, CodeLlama-34B, WizardCoder-34B and WizardCoder-34B, the average length of human code that was wrongly identified as AI-generated was significantly shorter than that of correctly classified human code. The length differences were 143.16, 152.40 and 133.65 characters respectively. This consistent trend indicates that human implementations with shorter code lengths are more likely to trigger the classifier to misclassify as AI-generated. The reason for this is that short code typically has simpler functionality, its structure, function calls, and naming styles tend to be more direct. Humans and AI in such scenarios have highly overlapping implementation methods, resulting in insufficient distinguishing features and thus causing misclassification.

6.4.2 AI code misidentified as Human-generated feature analysis

Table 11 presents the comparison of the lengths of misclassified and correctly classified AI code. Except for GPT-3.5-Turbo, the average lengths of the AI code misclassified as human-written in the other three datasets were significantly shorter than those of the correctly classified AI code, with the length difference ranging from 280.80 to 394.93 characters. This pattern is similar to that of human code misclassification, where short, concise, and plain-styled AI-generated code is more likely to be misjudged as human work. However, the GPT-3.5-Turbo dataset shows a distinct pattern: the average length difference between misclassified and correctly classified AI code is only 5.70 characters, with almost no significant difference. This indicates that in the GPT-3.5-Turbo scenario, length is no longer the main factor affecting misclassification.

We further examined the AI code that was misclassified in the GPT-3.5-Turbo dataset and the corresponding human code samples. Given that the construction of this dataset was based on generating AI code and collecting human code from the same text prompts, we infer that when the original prompt is detailed enough to limit the implementation details, GPT-3.5-Turbo(as the model with the strongest generation ability among the four) can reproduce an implementation that is almost indistinguishable from human code. At this point, the classifier is unable to extract effective distinguishing features at the semantic or structural level, resulting in an increase in the misclassification rate.

In conclusion, the misclassification analysis reveals two main findings: Firstly, simple and short-functioning code, whether written by humans or AI, tends to have similar styles, resulting in blurred features; Secondly, strong generative models such as GPT-3.5, when given specific prompts, output samples that are highly consistent with human code, fundamentally challenging the decision boundaries of binary classifiers. Future improvement directions could consider introducing external semantic information, such as the perplexity of code tokens, to distinguish subtle features such as changes in the choice of variable words

6.6 Rationale and comparative analysis of encoder selection

6.6.1 Rationale for encoder selection

In this section, we will explain why we chose a pure encoder architecture and why we chose a combination of CodeBERT and UniXcoder models.

We decided to adopt the pure encoder architecture because research (Liu 2024) has shown that pure encoder models perform exceptionally well in language understanding tasks: pure encoders, with a much smaller parameter size, can outperform encoder-decoder models and pure decoder models with tens of times larger parameter sizes, and have higher training and parameter efficiency.study. This study demonstrated that pure encoder models perform exceptionally well in language understanding tasks: a pure encoder with a much smaller parameter size can outperform encoder-decoder models and pure decoder models that are tens of times larger in terms of parameters, and it also has higher training efficiency and parameter efficiency.

And we chose the CodeBERT and UniXcoder encoder combination for the following reasons:

  • Semantic understanding with CodeBERT: By pre-training on code-language pairs, CodeBERT learns to associate code snippets with their functional intent. This capability is crucial for detecting functionally similar but differently implemented code—a common trait in AI-generated samples. It excels at capturing semantic cues from variable names, comments, and overall logic.

  • Syntactic modeling with UniXcoder: UniXcoder’s integration of AST and data flow information during pre-training gives it an edge in recognizing structural patterns. For Go, where adherence to formatting and idiomatic constructs is paramount, UniXcoder can flag syntactical anomalies that may signal AI authorship.

  • Combined advantage: The interplay of these two models provides a comprehensive feature set that covers both high-level intent and low-level structure. This dual perspective enhances both the accuracy and robustness of detection, particularly for Go’s concise and well-defined programming paradigm.

6.6.2 Analysis of different encoder combinations

Experimental results(Table 16) show that the combination of UniXcoder and CodeBERT achieves optimal or most stable performance on all four datasets(e.g., an F1-score of 0.9281 on GPT-3.5-Turbo and 0.9783 on CodeLlama-34B), validating the rationality and effectiveness of this model combination. In contrast, the combination of GraphCodeBERT with other models performs poorly, mainly for the following reasons:

Individual performance disadvantage: GraphCodeBERT’s individual detection performance is generally lower than UniXcoder(e.g., an F1-score of 0.8277 vs. 0.9185 on GPT-3.5-Turbo), resulting in limited improvement when combined with CodeBERT(CodeBERT+GraphCodeBERT’s F1-score is only 0.8309), far lower than UniXcoder+CodeBERT’s 0.9281.

Insufficient Feature Complementarity: Both GraphCodeBERT and UniXcoder focus on learning code syntax structure(such as data flow). Their feature spaces are similar, making it difficult to provide effective complementary information when fused; instead, it may introduce noise. For example, on the CodeLlama-34B dataset, the F1-score of UniXcoder+GraphCodeBERT(0.9581) is even lower than that of UniXcoder alone(0.9600), indicating a negative effect of the combination.

In summary, UniXcoder + CodeBERT is a suitable combination due to their strong complementarity. GraphCodeBERT, on the other hand, offers limited improvement when combined with other models due to its performance limitations and feature overlap issues.

6.7 Practical applications

Our method, a dual-encoder fusion detection approach for the Go programming language, demonstrates practical value in distinguishing between AI-generated code and human-written code.

In code review scenarios, this method can be integrated into CI/CD pipelines. By extracting code snippets and outputting probability scores, it assists reviewers in focusing on the originality, compliance, and potential risks of the code, improving review efficiency.

In terms of security strategies, GoDED can act as a detection engine to analyze suspicious code, triggering alerts for samples exceeding preset thresholds. This helps security teams identify AI-generated attack payloads and take timely defensive measures.

In the field of academic integrity, this method can automatically detect and generate reports on programming assignments, assisting teachers in making comprehensive judgments to maintain academic integrity, while also guiding students to use auxiliary tools appropriately during their learning process.

By fusing the semantic information of CodeBERT with the syntactic structural features of UniXcoder, our method can provide more accurate and stable detection results in these practical applications, providing strong support for related fields.

6.8 Limitations and future work

Despite the promising results of our dual-encoder approach for detecting AI-generated Go code, several limitations remain, which also point to directions for future research.

Data coverage and model generalization

Our dataset primarily relies on code generated by GPT-3.5-Turbo, CodeLlama, and WizardCoder. Given the rapid evolution of code generation models (e.g., GPT-4, CodeT5+, Gemini), the generalizability of our method to newer architectures is yet to be verified. Future work should construct multilingual and multi-model datasets to evaluate cross-model transferability and extend the approach to other programming languages such as Python and Java.

Sensitivity to format variations

While we investigated the impact of indentation, other coding style differences (e.g., spacing, line breaks, bracket placement) have not been systematically evaluated. Although indentation can be normalized, broader stylistic sensitivity requires further study. Future research will examine a wider range of formatting conventions and their effects on detection performance.

Computational overhead

The dual-encoder architecture significantly increases training time and GPU memory usage compared to single-encoder baselines, which may hinder deployment in resource-constrained scenarios. To address this, we plan to explore lightweight model variants through knowledge distillation and model pruning, enabling real-time applications.

Robustness to adversarial, hybrid, and obfuscated code

The current evaluation lacks standardized datasets for adversarial, hybrid, or obfuscated Go code, and the absence of full compilation contexts limits robustness testing. Since our method relies on semantic and syntactic feature fusion, it may be vulnerable to disruptions. Future work will involve creating benchmark datasets and investigating defense mechanisms such as adversarial training to enhance robustness. Additionally, integrating explicit Go language knowledge (e.g., syntactic rules, static analysis) may help capture idiomatic patterns and improve resilience.

7 Conclusion

This study proposes a dual-encoder fusion method for detecting Go code generated by artificial intelligence, aiming to overcome the limitations of existing methods that rely solely on single-dimensional features. Through comprehensive experiments and analysis, we have verified the effectiveness, robustness and interpretability of the proposed method.

First, on the first three datasets we constructed, our method outperformed the baseline methods by achieving higher F1 scores and ROC AUC values. And on the last dataset, it also achieved the same excellent detection performance as other baseline methods. This confirms that the integration of semantic features and syntactic features can provide a more comprehensive and distinct representation.

Secondly, the qualitative and quantitative analysis based on embedding visualization and cosine similarity indicates that our method can learn a more separable and compact feature space. The ablation study further confirmed the necessity of the two encoders and the importance of the adaptive fusion mechanism. Although a single encoder only has partial discrimination ability, by combining the two through deep interaction, the best performance can be achieved when both types of features are strong.

Thirdly, the error classification analysis has revealed the key patterns that affect the accuracy of detection. Whether it is human-written or AI-written short and functionally simple code, they often have similar styles, leading to ambiguous classification. Moreover, powerful generation models like GPT-3.5, when given detailed instructions, can generate code that is almost identical to that achieved by humans, posing a fundamental challenge to binary classifiers. These findings indicate that more refined features need to be introduced.

Finally, we acknowledge that this study has some limitations, including a limited model coverage, high computational cost, and insufficient robustness assessment for adversarial, hybrid, or obfuscated code. Future work will expand to more programming languages, develop lightweight versions for deployment, incorporate explicit language knowledge, and systematically evaluate the model’s robustness.

In conclusion, this work has laid a solid foundation for detecting code generated by artificial intelligence in real-world scenarios. By combining semantic understanding with syntactic structure analysis, our method not only improves the detection accuracy but also provides interpretable insights into the behavior patterns of the generation model. We believe that this dual-encoder model can be extended to other programming languages and detection tasks, providing risk warnings and decision support for engineering practice, ensuring the traceability and intellectual property rights of code assets, and maintaining the fairness and academic integrity of programming ability cultivation.

1.1 B.1 Preliminary evaluation results of the original Doc2Code-LLM dataset

To illustrate the necessity of data cleaning and format standardization, we conducted preliminary classification experiments on the original CCD dataset(Go programming language portion) without indentation normalization. The experiments used the same training split and evaluation metrics, and we summarize the results in Tables 18, 19, 20 and 21.

The experimental results show that, on the original data, the classification accuracy of the baseline method based on the pre-trained model is mostly close to 100%. Analysis reveals that this phenomenon is not because the model truly understands the semantics of the code, but rather due to a systematic bias in the format of the data itself: human-written code has inconsistent indentation styles(such as using tabs or variable-length spaces), while AI-generated code generally uses standard 4-space indentation. Therefore, the model can achieve near-perfect classification simply by capturing this superficial feature of indentation patterns. In real-world applications, attackers can easily bypass detection by simply adjusting code indentation, leading to a significant decrease in the model’s generalization ability.

Appendix C

1.1 C.1 Data preprocessing methods

Extraction of original indentation

We first read the source code text and locate all newline characters (\n). For each subsequent line after a newline character, we precisely count the number of consecutive blank characters at the beginning of the line (since tab characters (\t) are not present in the known data, all indentations are composed of spaces). Thus, we obtain an “original indentation space count” for each line of code.

Logical hierarchy mapping

Next, we remove duplicates from the “original indentation space counts” of all lines to obtain an independent set of numerical values. Then, we sort and grade these values based on their own magnitudes, rather than pre-assuming a fixed indentation base(such as 2 or 4 spaces). Specifically, all different indentation space counts that have occurred are sorted in ascending order. The smallest non-zero value is mapped to logical level 1, the second smallest to logical level 2, and so on. For example, if the set of indentation space counts in the original data is \( \{0, 2, 4, 6\} \), the mapping relationship is: \(0\) spaces \(\rightarrow \) level 0, \(2\) spaces \(\rightarrow \) level 1, \(4\) spaces \(\rightarrow \) level 2, \(6\) spaces \(\rightarrow \) level 3. If the set of indentation space counts in the original data is \( \{0, 4, 8, 12\} \), the mapping relationship is: \(0\) spaces \(\rightarrow \) level 0, \(4\) spaces \(\rightarrow \) level 1, \(8\) spaces \(\rightarrow \) level 2, \(12\) spaces \(\rightarrow \) level 3. This method ensures that any original indentation pattern that increases by a fixed difference(whether 2, 4, or 6) can be losslessly, proportionally converted into an integer logical hierarchy sequence starting from level 1.

Standardization rewriting

Finally, to ensure that the entire dataset conforms to the universal 4-space indentation standard, we convert the logical hierarchy obtained in the previous step into the corresponding number of spaces. The specific approach is that each logical hierarchy represents one level of indentation, and each level of indentation uses 4 spaces. Therefore, the total number of indentation spaces is the number of levels of the logical hierarchy multiplied by 4. Logical 0 level(i.e., no indentation) corresponds to 0 spaces, logical 1 level corresponds to 4 spaces, logical 2 level corresponds to 8 spaces, and so on. Subsequently, based on this mapping relationship, we rewrite the leading blank parts of all lines, thereby completing the automated and standardized correction of the indentation style throughout the code base.

This process is executed automatically through a self-developed Python script, ensuring efficiency and absolute consistency in processing. This method is directly based on the statistical characteristics of the data for conversion, and any researcher can reproduce exactly the same standardized results according to the above steps.
