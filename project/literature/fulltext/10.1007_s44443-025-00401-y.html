Abstract

Just-In-Time Defect Prediction (JITDP), as an important means to improve software quality and reduce maintenance costs, has received widespread attention in recent years. However, existing methods generally neglect multi-scale temporal features during the development process, lack dynamic modeling of developer behavior and project lifecycle, and have limited robustness when facing concept drift. To address these limitations, this paper proposes a novel Multi-Scale Temporal Defect Prediction framework (MSTDP) that integrates commit behavior patterns at temporal granularities of hours, days, and weeks, combining code semantic information, developer behavioral features, and lifecycle-aware mechanisms to comprehensively characterize the dynamic evolution patterns of defect introduction. MSTDP achieves deep feature fusion through cross-attention mechanisms and constructs a concept drift analysis module to enhance the model’s adaptability across different evolutionary stages. Empirical results on 9 large-scale open-source projects demonstrate that MSTDP achieves optimal performance across all evaluation metrics: average accuracy of 76.89% (0.56% improvement), precision of 61.02% (0.53% improvement), recall of 67.82% (0.64% improvement), F1-score of 60.93% (0.46% improvement), and AUC of 81.88% (0.52% improvement), significantly outperforming 7 mainstream baseline methods including JITBoost, FENSE, and JIT-CF. Wilcoxon signed-rank tests confirm the statistical significance of these improvements (\(\varvec{p < 0.05}\)). The research results validate the effectiveness of this method for efficient and accurate defect prediction in dynamic software engineering environments, demonstrating stronger generalization capability and robustness against concept drift.

1 Introduction

Software defects represent one of the most challenging problems in modern software development, significantly impacting project costs, quality, and security. Statistics indicate that the cost of software defect repair grows exponentially with the delay in defect discovery, with early-detected defects costing only one-tenth of those discovered later. More critically, software defects can lead to system crashes, data loss, and even security vulnerabilities, causing enormous losses to enterprises and users (McIntosh et al. 2016). Therefore, how to timely and accurately identify and prevent defect introduction during the software development process has become a core research topic in the field of software engineering.

Traditional defect prediction methods primarily rely on file-level static analysis, determining whether files contain defects by analyzing code complexity, file size, and other metrics. However, these methods suffer from obvious timeliness issues: when prediction results indicate that a file may contain defects, the file often already contains numerous code changes, making it extremely difficult to locate specific defect introduction points. In contrast, Just-in-Time (JIT) defect prediction technology can determine whether a code change will introduce defects at the moment of code commit (Kamei et al. 2018). This prediction approach offers three significant advantages: first, it provides more timely feedback, enabling developers to immediately fix issues while their memory is fresh; second, it refines prediction granularity to specific code changes, greatly reducing the difficulty of defect localization; finally, it supports more actionable quality assurance measures, such as targeted code reviews and enhanced testing.

Although JIT defect prediction technology has achieved significant progress (Catolino et al. 2022; Wen et al. 2024; Wang et al. 2022), existing methods still have four key limitations. First, most methods overly rely on static code metrics extracted from individual commits, such as lines of code changes and number of file modifications. While these metrics are intuitive, they lack understanding of deep code semantics (Alsolai and Roper 2022; Ju et al. 2022). Second, existing methods generally ignore the temporal dynamic characteristics inherent in software development as a continuous process, failing to effectively capture development patterns and rhythm changes across different time scales (Lu et al. 2025; Liu et al. 2024b). For example, frequent commits in the short term may reflect development pressure or emergency fixes, while long-term commit trends may reveal technical debt accumulation in projects. Third, modeling of developer behavior patterns is oversimplified, typically considering only developers’ overall experience values while ignoring individualized characteristics such as commit habits, coding styles, and expertise in specific technical domains (Catolino et al. 2022). Finally, existing methods adopt a ”one-size-fits-all” prediction strategy, failing to consider the different defect introduction patterns exhibited by software projects in different lifecycle stages (such as early rapid development, mid-term feature completion, and late-stage maintenance phases) (McIntosh et al. 2016; Cabral et al. 2021; Pachouly et al. 2022). Moreover, while algorithmic advances in related fields such as intelligent rehabilitation systems have demonstrated the effectiveness of combining 3D deep learning with point cloud processing for enhanced human-machine interaction (Xing et al. 2025b, a), similar multi-modal deep learning approaches remain underexplored in software defect prediction contexts.

The fundamental cause of these limitations lies in existing methods treating code changes as isolated, static events for analysis, while ignoring the essential characteristics of software development: it is a complex dynamic process involving multiple developers, spanning multiple time scales, and continuously evolving. In this process, the quality of code changes depends not only on the technical characteristics of the changes themselves, but is also profoundly influenced by various contextual factors such as development timing, developer status, and project stages. Therefore, constructing a JIT defect prediction method that can comprehensively model these dynamic factors has become an urgent problem to be solved.

Based on the above analysis, this research addresses key challenges in JIT defect prediction and proposes three core research questions:

\(\bullet \) RQ1: Can multi-scale temporal feature extraction improve JIT defect prediction performance? Specifically, how much do feature patterns at different time scales (e.g., hours, days, weeks) contribute to defect prediction, and how can we effectively fuse these multi-scale temporal information to improve prediction accuracy?

\(\bullet \) RQ2: What roles do factors such as developer behavior and project lifecycle play in defect prediction? Specifically, how do developers’ historical behavior patterns and the evolutionary stage of projects affect the probability of defect introduction, and how can our model explicitly characterize and utilize these factors?

\(\bullet \) RQ3: What kind of robustness does the proposed method have against concept drift? As time progresses and projects evolve, defect patterns may change. Can our method maintain stable prediction performance and adapt to changes when facing such concept drift?

To systematically address the above research questions, this paper proposes a Multi-Scale Temporal Defect Prediction (MSTDP) framework and makes the following five main contributions:

1. Multi-scale Temporal Feature Extraction Method This paper proposes a systematic multi-scale temporal feature extraction method that can simultaneously capture software development patterns across three time scales: hours, days, and weeks. This method constructs temporal feature sequences through sliding window techniques, models temporal dependencies using Long Short-Term Memory (LSTM) networks, and fuses information from different scales through adaptive attention mechanisms (Ju et al. 2025a, b; Matloob et al. 2021). Experimental validation demonstrates that this approach provides effective technical solutions for accurately capturing development dynamics at different temporal granularities.

2. Integrated Neural Network Architecture Design This paper designs an end-to-end deep learning architecture that achieves deep fusion of code semantic features and temporal patterns through cross-attention mechanisms (Ju et al. 2022; Lu et al. 2025). This architecture breaks through the limitations of simple feature concatenation in traditional methods and can learn complex nonlinear interaction relationships between different types of features. Through this deep fusion, the model can understand the semantic associations between ”code change content” and ”change temporal patterns,” thereby enabling more accurate defect predictions.

3. Developer Behavior Modeling and Project Lifecycle Awareness This paper proposes a multi-dimensional developer behavior modeling method that comprehensively characterizes developer features through three dimensions: developer identity encoding, commit pattern analysis, and experience feature encoding (Catolino et al. 2022). Meanwhile, a project lifecycle awareness module is designed that can automatically identify the current project stage and adopt corresponding expert prediction strategies. This comprehensive modeling approach addresses the limitations of oversimplified developer representation and uniform prediction strategies in existing methods.

4. Concept Drift Analysis Framework This paper establishes a systematic concept drift analysis framework for evaluating the adaptive capability of prediction models when facing long-term project evolution (Cabral et al. 2021; Chen et al. 2024c). This framework not only evaluates the overall robustness of models but also analyzes the performance differences of different components under concept drift conditions. Through this analysis, the research reveals the mechanisms and extent to which multi-scale temporal modeling contributes to concept drift adaptation capability.

5. Comprehensive Experimental Validation This paper conducts comprehensive experimental validation on multiple large-scale open-source projects including representative projects such as Brackets, Broadleaf, and Fabric (Al-Khiaty et al. 2023; Giray et al. 2023). Experimental results demonstrate that the MSTDP method achieves superior performance compared to existing state-of-the-art methods across multiple metrics. Particularly in handling concept drift, this method demonstrates enhanced robustness, providing technical support for the practical application of JIT defect prediction technology.

The remainder of this paper is organized as follows: Section 2 reviews related work, analyzes the shortcomings of existing research and clarifies the entry point of this research; Section 3 details the framework and implementation details of the MSTDP method; Section 4 presents experimental design, performance comparison, and ablation studies, with particular focus on evaluating the model’s robustness in handling concept drift; Section 5 discusses the validity threats of this research; Section 6 summarizes the research conclusions of this paper.

2 Related work

Just-in-Time (JIT) software defect prediction, as a key technology for software quality assurance, aims to identify whether defects are introduced at the moment of code commit or change, thereby achieving early intervention at the lowest cost. In recent years, both academia and industry have invested substantial research in this field, proposing rich solutions from multiple dimensions including feature engineering, modeling methods, and addressing practical challenges. This section will systematically review these related works and clarify the limitations of existing methods, thereby highlighting the motivation and contributions of this research (Akimova et al. 2021; Munir et al. 2021).

2.1 JIT prediction methods based on feature engineering and representation learning

The performance of JIT prediction largely depends on how to effectively characterize a code change. Early research primarily relied on carefully designed handcrafted features. For example, Kamei et al. (2018) proposed a classic feature set containing 14 metrics covering aspects such as change size, history, and developer experience, laying the foundation for numerous subsequent studies. Researchers continuously attempted to expand this feature space, such as Catolino et al. (2022) who significantly improved model performance by introducing novel “developer-centric” features including developer social and organizational aspects. Wen et al. (2024) took a different approach by classifying commits by intent (such as feature enhancement, bug fix) and constructing specialized models (CC-JITDP) to improve prediction accuracy. However, while these handcrafted features have good interpretability, their construction process is time-consuming and labor-intensive, and may fail to capture deep semantic information in code.

To overcome the limitations of handcrafted features, deep learning techniques have been widely applied to automatically learn representations of code changes. Some work focuses on learning from raw or structured code information. For example, Wang et al. (2022) proposed AC-JIT, which captures fine-grained code structural changes by learning Abstract Syntax Tree (AST) change sequences; Alsolai and Roper (2022) applied CNN-LSTM models to automatically learn semantic features from textual information such as commit logs. To combine the advantages of different types of features, Ju et al. (2022) proposed JIT-HF, combining deep semantic features extracted by CodeBERT with traditional handcrafted features. Lu et al. (2025) further designed a bi-modal fusion framework BM-JITDP, effectively fusing code semantics and handcrafted features through attention mechanisms. Another part of research explores more complex code representations, such as using Code Property Graphs (CPG) and Graph Neural Networks (GNN). Liu et al. (2024b) proposed the JIT-DCP method based on this approach, achieving more precise defect count prediction; Wang et al. (2024) used code graph representation learning to localize defects at the file level.

To further improve the quality of feature representations, some studies introduced more advanced representation learning and feature selection techniques. Ju et al. (2025a) obtained more discriminative feature representations (JIT-CF) by integrating contrastive learning; Ju et al. (2025b) leveraged the powerful feature interaction learning capability of Transformers to address cross-project prediction problems (CT-JITDP); Zhou et al. (2024b) used sequential forward feature selection algorithms to eliminate feature redundancy (SF-JITDP), improving model efficiency.

Overall, whether using handcrafted features or deep representation learning, most existing work treats a code change as an isolated, static snapshot for analysis. They focus on mining as much information as possible within individual commits, but generally ignore the temporal dimension inherent in software development as a continuous process, failing to effectively model temporal dependencies and development rhythms between code changes at the levels of hours, days, weeks, etc.

2.2 Research addressing practical challenges in JIT prediction

Beyond improving model accuracy, many studies have also addressed challenges faced by JIT prediction in practical applications, such as data imbalance, review costs, and cross-project prediction.

\(\bullet \) Data Imbalance and Label Noise: Since defect-introducing commits are typically the minority class, data imbalance seriously affects model performance. To address this, Zhou et al. (2024a) proposed FABA-JIT, using feature-aware attention mechanisms combined with balanced loss functions. Chen et al. (2024a) proposed a time-weight-aware oversampling method TWAO, giving higher weights to recent data when generating new samples. Considering that ”clean” labels may also contain undiscovered defects, Liu et al. (2024a) innovatively formulated JIT prediction as a Positive and Unlabeled (PU) learning problem, improving model robustness to label noise.

\(\bullet \) Effort-Aware and Automated Modeling: To make prediction results more practically valuable, Ni et al. (2024) proposed weighted multi-objective optimization algorithms, achieving better balance between performance and cost in effort-aware prediction. Liu et al. (2020) combined effort-awareness with semi-supervised learning (ESS-JITDP) to utilize large amounts of unlabeled data. To reduce modeling complexity, Chen et al. (2023) proposed AutoJIT, using Automated Machine Learning (AutoML) to automatically select and optimize prediction models.

\(\bullet \) Cross-Project Prediction: To address the “cold start” problem of new projects lacking historical data, researchers explored Cross-Project Defect Prediction (CPDP). Chen et al. (2024b) designed an online cross-project prediction framework COJIT, enabling models to quickly adapt to new projects through selective retraining strategies.

These studies have greatly improved the practicality and robustness of JIT prediction, but they mainly innovate in learning strategies and optimization objectives. The feature sets their models rely on are mostly still static, failing to incorporate rich contextual information such as the dynamics of the development process, evolution of developer behavior, and the lifecycle stage of projects.

2.3 Strategies for addressing concept drift

Software projects continuously evolve, with their technology stacks, team members, and development practices changing over time, leading to changes in defect introduction patterns—a phenomenon known as “concept drift.” Extensive empirical studies by McIntosh et al. (2016) and Cabral et al. (2021) have confirmed that concept drift has significant negative impacts on JIT prediction model performance.

Current methods for addressing concept drift are mostly passive online learning or model update strategies. For example, Chen et al. (2024c) designed a reliable semi-supervised framework ROS-JIT for online scenarios, adapting to drift by monitoring model performance and dynamically updating. Li et al. (2025) went further by designing a ”human-in-the-loop” online learning framework, using active learning to request annotations from domain experts to respond to environmental changes. Trautsch et al. (2022) also designed a standardized continuous evaluation process to measure model performance degradation in real development environments.

However, the core idea of these methods lies in “detection and reaction,” i.e., taking remedial measures after model performance degrades. They lack a mechanism for proactive prediction and autonomous adaptation, failing to build model architectures that can anticipate and inherently adapt to concept drift based on the intrinsic patterns of project evolution (such as stage transitions from rapid development to long-term maintenance).

2.4 Other related research

The JIT prediction field has also seen many other dimensions of research. In terms of application extension, researchers have applied JIT technology to more fine-grained defect localization (Lin et al. 2025; Wang et al. 2023; Huang et al. 2022), or applied it to specific domains such as performance regression defects (Luo et al. 2023), log-inducing defects (He et al. 2024), autonomous driving systems (Chen et al. 2024d), and multi-language projects (Chen et al. 2024e). In terms of interpretability and tooling, to improve model transparency and usability, Li et al. (2024), Shehab et al. (2022), and Al-Khiaty et al. (2022) developed tools such as CfExplainer, JITBot, and PyExplainer respectively, providing explanations for prediction results and integrating them into development workflows. Additionally, some foundational work has also contributed to field development, such as Tabassum et al. (2022) revealing the impact of “duplicate changes” on prediction, and Al-Khiaty et al. (2023) constructing and releasing the high-quality large-scale dataset Defectors.

2.5 Limitations of existing research and the entry point of this study

Based on the above analysis, although existing JIT defect prediction research has made significant progress, several key, systematic limitations remain:

1. Insufficient Utilization of Temporal Information: Most methods treat code changes as independent static events, ignoring the complex temporal patterns and development rhythms that software development exhibits across different time scales such as hours, days, and weeks.

2. Simple Multi-dimensional Feature Fusion Mechanisms: When fusing multi-dimensional features such as code, developer, and historical features, existing methods mostly use simple concatenation or linear combination, making it difficult to capture deep, nonlinear interactions between them.

3. Single-dimensional Developer Behavior Modeling: Modeling of developer factors is usually limited to static indicators such as experience values, failing to adequately characterize dynamic behavior patterns such as developer commit habits and recent activity levels, and their changes over time.

4. Limited Concept Drift Adaptation Capability: Existing methods for addressing concept drift are mostly passive updates, lacking intrinsic mechanisms that can proactively perceive project evolution stages and autonomously adjust prediction strategies.

To systematically address the above problems, this paper proposes a Multi-Scale Temporal Defect Prediction (MSTDP) framework. This framework captures multi-scale development patterns through deep temporal networks, uses cross-attention mechanisms to deeply fuse multi-dimensional information including code semantics, temporal patterns, developer behavior, and project lifecycle, aiming to significantly improve the accuracy, robustness, and adaptability of JIT defect prediction to dynamic software development environments.

3 Methodology

This section provides a detailed introduction to our proposed Multi-Scale Temporal Defect Prediction (MSTDP) method. This method significantly improves the accuracy and robustness of just-in-time software defect prediction by integrating multi-scale temporal information, code semantics, developer behavior patterns, and project lifecycle awareness. Figure 1 shows the overall flow architecture of the method, and Fig. 2 provides a detailed description of the model’s internal structure.

As shown in Fig. 1, our MSTDP method adopts an end-to-end deep learning architecture, with the entire workflow divided into three main stages:

Stage 1: Data preparation & feature construction

  • Raw Data Ingestion: Extract commit history data from open-source software projects (such as Brackets, Broadleaf, Fabric, etc.)

  • Multi-dimensional Feature Extraction: Annotate defect-introducing commits through the SZZ algorithm and apply feature engineering techniques to extract features from five dimensions:

    • Change Size features: number of modified files, lines of code changes, etc.

    • File History features: file modification history, defect history, etc.

    • Diffusion features: change diffusion scope, number of affected subsystems, etc.

    • Developer Experience features: overall developer expe-rience, recent experience, subsystem experience, etc.

    • Change Purpose features: fix types, feature enhancements, etc.

Stage 2: Model architecture design

  • Multi-Scale Temporal Module: Processes temporal features at three time scales (hourly, daily, weekly) separately, fusing multi-scale information through LSTM networks and attention mechanisms

  • Semantic Temporal Fusion Module: Uses cross-atten-tion mechanisms to perform deep fusion of code semantic features with temporal representations

  • Developer Behavior Analysis Module: Models developer behavior through developer identity encoding, commit pattern analysis, and experience feature encoding

  • Project Lifecycle Aware Module: Identifies the current project stage (early/middle/late) and adopts corresponding expert prediction strategies

Stage 3: Training & inference output

  • Training Phase: Train the MSTDP model using historical annotated data, performing supervised learning with defect labels obtained through the SZZ algorithm

  • Inference Phase: Perform real-time defect prediction on new commits, outputting defect probability (0%-100%) and binary classification results (defective/clean)

3.1 Problem formalization

We model just-in-time defect prediction as a binary classification problem, with the goal of predicting whether a software change (commit) will introduce defects. Given a historical commit corpus \(C = \{c_1, c_2, \ldots , c_n\}\) and their corresponding labels \(Y = \{y_1, y_2, \ldots , y_n\}\), where \(y_i \in \{0,1\}\) indicates whether commit \(c_i\) contains defects (1 indicates contains, 0 indicates does not contain), our goal is to learn a prediction function \(f: C \rightarrow \{0,1\}\) that outputs the probability of a new commit containing defects.

Each commit \(c_i\) is associated with a timestamp \(t_i\), code changes \(\Delta _i\), metadata \(M_i\) (including developer information), and historical context \(H_i\), which contains all commits that temporally precede \(c_i\):

$$\begin{aligned} H_i = \{c_j | t_j < t_i, c_j \in C\} \end{aligned}$$
(1)

Unlike previous methods that primarily rely on static features extracted from individual commits, our MSTDP method integrates:

  1. 1.

    Multi-scale temporal information extracted from \(H_i\) at different time granularities

  2. 2.

    Semantic representations of code changes \(\Delta _i\)

  3. 3.

    Developer behavior patterns derived from commit history

  4. 4.

    Project lifecycle context inferred from repository evolution

This comprehensive modeling of commit context enables our method to capture the complex factors that influence defect introduction in software development.

3.2 Multi-scale temporal feature extraction

Software development is inherently a complex temporal process, and defect introduction is often not an isolated event but stems from complex interaction patterns occurring over different time periods. Traditional JIT defect prediction methods primarily focus on static features of individual commits, such as code complexity and number of file modifications, but this approach has three key limitations:

  1. 1.

    Ignoring the impact of development rhythm: Rapid consecutive commits may indicate emergency fixes or development pressure, patterns that are most evident at the hourly level

  2. 2.

    Lack of medium-term pattern recognition: Daily-level development patterns can reflect developer work habits and project iteration cycles

  3. 3.

    Missing long-term trend analysis: Weekly-level trends can reveal technical debt accumulation and architectural evolution in projects

To capture these multi-level temporal patterns, we introduce a multi-scale temporal feature extraction method that analyzes commit history at three different time scales.

3.2.1 Temporal scales and feature windows

We define three temporal scales to capture development dynamics at different granularities:

  1. 1.

    Hourly Scale (\(W_h\)): Captures short-term development activities and immediate changes (24-hour window)

  2. 2.

    Daily Scale (\(W_d\)): Captures medium-term development patterns (7-day window)

  3. 3.

    Weekly Scale (\(W_w\)): Captures long-term project trends (4-week window)

For each commit \(c_i\) with timestamp \(t_i\), we use sliding window techniques to extract temporal features from historical commits within these three time windows. For each temporal scale \(s \in \{W_h, W_d, W_w\}\) and window size \(w_s\), we define an interval sequence:

$$\begin{aligned} I_{s,i} = \{[t_i - (w_s - j + 1) \cdot \delta _s, t_i - (w_s - j) \cdot \delta _s] | j \in \{1,2,\ldots ,w_s\}\} \end{aligned}$$
(2)

where \(\delta _s\) is the step size (time interval) corresponding to scale s:

$$\begin{aligned} \delta _{W_h}&= 3600 \text { seconds (1 hour)} \end{aligned}$$
(3)
$$\begin{aligned} \delta _{W_d}&= 86400 \text { seconds (1 day)} \end{aligned}$$
(4)
$$\begin{aligned} \delta _{W_w}&= 604800 \text { seconds (1 week)} \end{aligned}$$
(5)

These window sizes were chosen based on established software development cadences and agile methodologies.

  • Hourly Scale (\(W_h\), 24 hours): This window is designed to capture the immediate, micro-level context of a commit. It models the developer’s short-term ”burst” activity, development rhythm within a single workday (e.g., commits bunched before a daily stand-up), or signs of rushed work (e.g., many rapid-fire commits), which are strong short-term predictors of errors.

  • Daily Scale (\(W_d\), 7 days): This window aligns with the typical weekly work pattern. It captures the context of a standard workweek or a one-week sprint cycle. This scale can identify patterns related to ”end-of-week” rushes to merge features or developer fatigue/productivity cycles across the week.

  • Weekly Scale (\(W_w\), 4 weeks): This window models the longer-term, macro-level project trend, roughly corresponding to a monthly release cycle or a typical agile sprint iteration (e.g., 2-4 weeks). This scale is crucial for identifying patterns of accumulating technical debt or the rhythm of the project leading up to a major deadline or release.

By combining these three theoretically-grounded scales, our model can create a richer, more robust temporal representation than any single, arbitrarily chosen window.

3.2.2 Feature sequence construction

For each interval in \(I_{s,i}\), we identify the most recent historical commit that falls within that interval. Formally, for each interval \([t_{start}, t_{end}] \in I_{s,i}\), we select:

$$\begin{aligned} c_j^* = \arg \max _{c_j \in H_i} t_j \text { s.t. } t_{start} \le t_j \le t_{end} \end{aligned}$$
(6)

If no commit exists within an interval, we use zero-padding mechanisms to maintain sequence length consistency. Features extracted from each selected commit form the temporal sequence \(T_{s,i}\) for temporal scale s:

$$\begin{aligned} T_{s,i} = \{f_{s,i}^1, f_{s,i}^2, \ldots , f_{s,i}^{w_s}\} \end{aligned}$$
(7)

where \(f_{s,i}^j\) represents the feature vector extracted from the commit selected for the j-th interval of \(I_{s,i}\), or a zero vector if no commit exists in that interval.

3.2.3 Feature normalization and extraction process

To ensure numerical stability during model training, we normalize all extracted features using min-max normalization:

$$\begin{aligned} f = \frac{f - \min (f)}{\max (f) - \min (f)} \end{aligned}$$
(8)

The feature extraction process follows Algorithm 1, ensuring that only historical information is used (commits with timestamps strictly less than the current commit timestamp), preventing data leakage that could artificially inflate performance metrics.

This extraction method enables our model to capture development patterns across multiple time scales, providing comprehensive temporal context for defect prediction.

3.3 MSTDP model architecture

Our MSTDP architecture consists of four major components: (1) multi-scale temporal module, (2) code semantic and temporal fusion, (3) developer behavior pattern analysis, and (4) project lifecycle awareness. These components work synergistically to provide comprehensive analysis of software changes. Figure 2 details the architecture of the proposed model.

3.3.1 Multi-scale temporal module

Existing JIT defect prediction methods have significant deficiencies in handling temporal information: most methods only consider linear temporal decay weights or simply use statistical features within fixed time windows. This simplified processing cannot capture the complex temporal dependencies in the software development process. For example, rapid iterations following an emergency fix may increase defect risk in the short term, while long-term technical debt accumulation requires longer time windows to identify.

To address this problem, we designed a multi-scale temporal module that can:

  • Adaptive weight allocation: Dynamically adjust the importance of different time scales through attention mechanisms

  • Sequential dependency modeling: Use LSTM networks to capture long- and short-term dependencies between temporal features

  • Multi-granularity fusion: Organically combine information from hourly, daily, and weekly scales

The multi-scale temporal module processes temporal data at different scales (hourly, daily, weekly) and fuses them through attention mechanisms. For commit \(c_i\), let \(T_{h,i}\), \(T_{d,i}\), and \(T_{w,i}\) be the temporal feature sequences at hourly, daily, and weekly scales, respectively. We use dedicated Long Short-Term Memory (LSTM) networks to process each sequence:

$$\begin{aligned} \textbf{h}_{h,i}, \textbf{c}_{h,i}&= \text {LSTM}_h(T_{h,i}) \end{aligned}$$
(9)
$$\begin{aligned} \textbf{h}_{d,i}, \textbf{c}_{d,i}&= \text {LSTM}_d(T_{d,i}) \end{aligned}$$
(10)
$$\begin{aligned} \textbf{h}_{w,i}, \textbf{c}_{w,i}&= \text {LSTM}_w(T_{w,i}) \end{aligned}$$
(11)

where \(\textbf{h}_{s,i}\) and \(\textbf{c}_{s,i}\) represent the hidden state and cell state of the LSTM for scale s, respectively. We take the final hidden state of each LSTM as the representation for that temporal scale:

$$\begin{aligned} \textbf{z}_{h,i}&= \textbf{h}_{h,i}[|W_h|] \end{aligned}$$
(12)
$$\begin{aligned} \textbf{z}_{d,i}&= \textbf{h}_{d,i}[|W_d|] \end{aligned}$$
(13)
$$\begin{aligned} \textbf{z}_{w,i}&= \textbf{h}_{w,i}[|W_w|] \end{aligned}$$
(14)

These representations are then concatenated and processed through an attention mechanism:

$$\begin{aligned} \textbf{z}_{\text {concat},i}&= [\textbf{z}_{h,i}; \textbf{z}_{d,i}; \textbf{z}_{w,i}] \end{aligned}$$
(15)
$$\begin{aligned} \textbf{a}_i&= \text {softmax}(W_a \cdot \textbf{z}_{\text {concat},i} + b_a) \end{aligned}$$
(16)

where \(W_a\) and \(b_a\) are learnable parameters, and \(\textbf{a}_i = [a_{h,i}, a_{d,i}, a_{w,i}]\) represents the attention weights for each temporal scale. The final multi-scale temporal representation is:

$$\begin{aligned} \textbf{z}_{\text {temporal},i} = a_{h,i} \cdot \textbf{z}_{h,i} + a_{d,i} \cdot \textbf{z}_{d,i} + a_{w,i} \cdot \textbf{z}_{w,i} \end{aligned}$$
(17)

This attention mechanism allows the model to adaptively focus on the most relevant temporal scales for each prediction, learning to adjust the relative importance of different time scales based on the characteristics of specific commits and project contexts.

3.3.2 Code semantic and temporal fusion

Traditional methods typically concatenate or linearly combine code features and temporal features, ignoring the deep semantic associations between them. In reality, there are important contextual relationships between the content of code changes (what changed) and the temporal patterns when changes occurred (when changed):

  • Relationship between code complexity and development pressure: Complex code modifications are more likely to introduce defects during high-pressure development periods

  • Association between modification scale and temporal patterns: Large-scale refactoring is usually accompanied by specific temporal patterns

  • Coupling of file types with development rhythm: Different types of files (e.g., configuration files vs. core logic) have different modification temporal characteristics

To effectively integrate code change information with temporal patterns, we introduce a cross-attention-based semantic-temporal fusion module. The rationale for using cross-attention is that the risk of a defect is not just a simple sum of the code’s complexity or the developer’s haste, but an interaction *between* them. For example, a highly complex change (semantic feature) made during a period of rapid, rushed commits (temporal pattern) may pose a much higher risk than the same complex change made during a normal development cycle.

To elaborate on the mechanism, the code semantic features (\(\textbf{z}_{\text {code},i}\)) serve as the Query (Q). This represents the question: ”Given *this specific code change* (e.g., large, complex, and impacting historical files)...” The temporal representations (\(\textbf{z}_{\text {temporal},i}\)) provide both the Keys (K) and Values (V). The Keys represent the ’context’ to be matched against the query (e.g., ’a high-pressure period’, ’a stable period’). The model calculates an attention score by matching the Query (code) against the Keys (temporal context). This score determines ’how much attention’ to pay to each part of the temporal context. Finally, these scores are used to create a weighted sum of the Values (which are also the temporal representations), producing a final fused vector \(\textbf{z}_{\text {fusion},i}\) that represents the temporal context *as it relates to the specific code change*. This allows the model to dynamically learn that, for instance, ’complex code’ (Q) should pay more attention to ’rushed commit patterns’ (K) to predict defects. In the context of this work, we define cross-modal fusion as the integration of two distinct information dimensions: the code semantic dimension (representing “what was changed”) and the temporal pattern dimension (representing “when changes occurred”). These two dimensions constitute different modalities of information in the software development process, where code semantics capture the structural and syntactic characteristics of changes, while temporal patterns capture the behavioral and contextual characteristics of the development process.

Let \(\textbf{x}_{\text {code},i}\) be the feature vector representing code changes in commit \(c_i\), including metrics such as added/deleted lines, number of modified files, and code complexity measures.

To elaborate on the composition of this vector, \(\textbf{x}_{\text {code},i}\) is a concatenation of established, process-agnostic code change metrics derived from the commit data, as popularized by Kamei et al. (2018). These metrics fall into three main categories:

  • Size Metrics: Lines of code added, deleted, and modified; total lines of code in the change.

  • Diffusion Metrics: Number of files modified, number of subsystems (directories) modified, number of unique file extensions.

  • History Metrics: Number of times the modified files were changed in the past, number of developers who previously modified the files.

First, we transform the raw code features into semantic representations:

$$\begin{aligned} \textbf{z}_{\text {code},i}&= \text {LayerNorm}(W_2 \cdot \text {ReLU}(\text {LayerNorm}\nonumber \\&\quad (W_1 \cdot \textbf{x}_{\text {code},i} + b_1) + b_2)) \end{aligned}$$
(18)

where \(W_1\), \(W_2\), \(b_1\), and \(b_2\) are learnable parameters, and LayerNorm denotes layer normalization.

The cross-attention mechanism enables deep interaction between code semantic features and temporal pattern features by learning dynamic attention weights that capture the contextual relationships between “what changed” and “when it changed”:

$$\begin{aligned} Q&= W_Q \cdot \textbf{z}_{\text {code},i}, \quad K = W_K \cdot \textbf{z}_{\text {temporal},i}, \quad V = W_V \cdot \textbf{z}_{\text {temporal},i} \end{aligned}$$
(19)
$$\begin{aligned} \alpha _i&= \text {softmax}\left( \frac{Q \cdot K^T}{\sqrt{d}}\right) \end{aligned}$$
(20)
$$\begin{aligned} \textbf{z}_{\text {fusion},i}&= \alpha _i \cdot V \end{aligned}$$
(21)

where \(W_Q\), \(W_K\), and \(W_V\) are learnable projection matrices, d is the dimension of the projection space, and \(\alpha _i\) represents the attention weights that quantify the relevance between specific code change characteristics and temporal development patterns.

The final semantic-temporal representation combines the cross-attention fusion result with the original code representation to preserve both the interactive information and the original semantic content:

$$\begin{aligned} \textbf{z}_{\text {st},i} = W_o \cdot [\textbf{z}_{\text {fusion},i}; \textbf{z}_{\text {code},i}] \end{aligned}$$
(22)

This cross-attention-based fusion mechanism allows the model to automatically discover and leverage the intricate relationships between code modifications and their temporal context. For example, the model can learn that complex refactoring operations during periods of high development activity may have different defect risk profiles compared to similar operations during stable maintenance phases. By explicitly modeling these cross-dimensional interactions, our approach transcends the limitations of simple feature concatenation and achieves a deeper understanding of the multifaceted nature of software defect introduction.

3.3.3 Developer behavior pattern analysis

Software development is a highly human-dependent creative process, and developers’ experience levels, work habits, and behavior patterns have decisive impacts on defect introduction. However, existing JIT defect prediction methods often oversimplify the modeling of developer factors, with the following main deficiencies:

  • Monolithic experience modeling: Only considering de-velopers’ overall experience while ignoring specialized experience in specific subsystems or technology stacks

  • Missing behavior patterns: Failing to capture developers’ commit habits, coding styles, and other individualized characteristics

  • Ignoring temporal evolution: Not considering the dynamic changes in developer experience and behavior over time

To comprehensively model developer factors, we designed a developer behavior pattern analysis module that captures developer-specific patterns from three dimensions:

Developer identity encoding

We use embedding layers to encode developer identity:

$$\begin{aligned} \textbf{e}_{\text {dev},i} = \text {Embedding}(d_i) \end{aligned}$$
(23)

where \(d_i\) is the ID of the developer who wrote commit \(c_i\).

Commit pattern analysis

We use LSTM to analyze developer commit patterns:

$$\begin{aligned} \textbf{p}_i = \text {LSTM}_{\text {pattern}}(\textbf{x}_{\text {pattern},i}) \end{aligned}$$
(24)

where \(\textbf{x}_{\text {pattern},i}\) represents features describing commit patterns (such as commit frequency, commit size distribution).

Experience feature encoding

We encode developer experience metrics:

$$\begin{aligned} \textbf{e}_{\text {exp},i} = W_{\text {exp}} \cdot \textbf{x}_{\text {exp},i} + b_{\text {exp}} \end{aligned}$$
(25)

where \(\textbf{x}_{\text {exp},i}\) includes experience features such as general experience (exp), recent experience (rexp), and subsystem-specific experience (sexp).

These components are fused to create a comprehensive representation of developer behavior:

$$\begin{aligned} \textbf{z}_{\text {dev},i} = \text {ReLU}(\text {LayerNorm}(W_{\text {dev}} \cdot [\textbf{e}_{\text {dev},i}; \textbf{p}_i; \textbf{e}_{\text {exp},i}] + b_{\text {dev}})) \end{aligned}$$
(26)

This module allows the model to learn developer-specific defect introduction patterns and how they evolve over time, capturing human factors that affect software quality.

3.3.4 Project lifecycle awareness

Software projects undergo significant evolution during their lifecycle, with fundamentally different defect introduction patterns at different stages. An important limitation of existing methods is using unified prediction models to handle all project stages, and this ”one-size-fits-all” approach cannot adapt to the complexity of project evolution:

  • Early stage: Rapid feature development, unstable architecture, high defect rate but relatively simple patterns

  • Middle stage: Feature improvement and optimization, frequent code refactoring, complex defect patterns

  • Late stage: Maintenance-oriented, cautious modifications, fewer defects but with significant impact

To address this problem, we propose a project lifecycle awareness module that can:

  • Automatically identify project stages: Determine current stage based on project timeline and development activity patterns

  • Expert strategy switching: Adopt specialized prediction strategies for different stages

  • Dynamic weight fusion: Dynamically combine predictions from different experts based on stage probabilities

Software projects evolve through different lifecycle stages, each with unique defect characteristics. Our project lifecycle awareness module adjusts prediction strategies based on the current lifecycle stage.

First, we estimate lifecycle stage probabilities:

$$\begin{aligned} \textbf{l}_i = \text {softmax}(W_{\text {lifecycle}} \cdot \text {ReLU}(W_{\text {pre}} \cdot \textbf{x}_{\text {lifecycle},i} + b_{\text {pre}}) + b_{\text {lifecycle}}) \end{aligned}$$
(27)

where \(\textbf{x}_{\text {lifecycle},i}\) are features indicating project lifecycle status (such as relative position in project timeline, commit frequency trends), and \(\textbf{l}_i = [l_{\text {early},i}, l_{\text {mid},i}, l_{\text {late},i}]\) represents the probabilities of the project being in early, middle, or late stages.

Then we employ specialized expert models for each lifecycle stage:

Each expert model (e.g., for \(\hat{y}_{\text {early},i}\), \(\hat{y}_{\text {mid},i}\), \(\hat{y}_{\text {late},i}\)) is implemented as a dedicated two-layer Multi-Layer Perceptron (MLP), as defined in (23)-(25). We deliberately chose a simpler architecture for these experts for two key reasons. First, it helps prevent overfitting to stage-specific data, which is by definition a smaller subset of the total data. Second, the primary complexity and feature learning are already captured by the shared feature extractors (the temporal, semantic, and developer modules); the expert models serve as specialized, lightweight decision heads to interpret these rich features based on the project’s evolutionary stage.

$$\begin{aligned} \hat{y}_{\text {early},i}&= \sigma (W_{\text {early}} \cdot \text {ReLU}(W'_{\text {early}} \cdot \textbf{x}_{\text {lifecycle},i} + b'_{\text {early}}) + b_{\text {early}}) \end{aligned}$$
(28)
$$\begin{aligned} \hat{y}_{\text {mid},i}&= \sigma (W_{\text {mid}} \cdot \text {ReLU}(W'_{\text {mid}} \cdot \textbf{x}_{\text {lifecycle},i} + b'_{\text {mid}}) + b_{\text {mid}}) \end{aligned}$$
(29)
$$\begin{aligned} \hat{y}_{\text {late},i}&= \sigma (W_{\text {late}} \cdot \text {ReLU}(W'_{\text {late}} \cdot \textbf{x}_{\text {lifecycle},i} + b'_{\text {late}}) + b_{\text {late}}) \end{aligned}$$
(30)

where \(\sigma \) is the sigmoid activation function. The final lifecycle-aware prediction is:

$$\begin{aligned} \textbf{z}_{\text {lifecycle},i} = l_{\text {early},i} \cdot \hat{y}_{\text {early},i} + l_{\text {mid},i} \cdot \hat{y}_{\text {mid},i} + l_{\text {late},i} \cdot \hat{y}_{\text {late},i} \end{aligned}$$
(31)

By explicitly modeling project lifecycle stages, our method can better adapt to the changing patterns of defect introduction as projects evolve from initial development to maintenance phases.

3.3.5 Final fusion and prediction

The outputs of all specialized modules are combined through a final fusion layer:

$$\begin{aligned} \textbf{z}_{\text {combined},i}&= [\textbf{z}_{\text {st},i}; \textbf{z}_{\text {dev},i}; \textbf{z}_{\text {lifecycle},i}] \end{aligned}$$
(32)
$$\begin{aligned} \hat{y}_i&= \sigma (W_{\text {final}} \cdot \text {Dropout}(\text {ReLU}(\text {LayerNorm}(W_{\text {pre-final}} \cdot \textbf{z}_{\text {combined},i} \nonumber \\&\quad + b_{\text {pre-final}}))) + b_{\text {final}}) \end{aligned}$$
(33)

where \(\hat{y}_i\) is the predicted probability that commit \(c_i\) contains defects. The final prediction is made through thresholding:

$$\begin{aligned} \text {prediction}_i = {\left\{ \begin{array}{ll} 1, & \text {if } \hat{y}_i \ge 0.5 \\ 0, & \text {otherwise} \end{array}\right. } \end{aligned}$$
(34)

This hierarchical fusion approach integrates insights from code semantics, temporal patterns, developer behavior, and project lifecycle to achieve more accurate defect prediction.

This extraction method enables our model to capture development patterns across multiple time scales, providing comprehensive temporal context for defect prediction.

3.4 Training strategy and implementation details

3.4.1 Loss function

We use binary cross-entropy loss combined with L2 regularization:

$$\begin{aligned} \mathcal {L} = -\frac{1}{N}\sum _{i=1}^{N}[y_i\log (\hat{y}_i) + (1-y_i)\log (1-\hat{y}_i)] + \lambda \sum _{j}\theta _j^2 \end{aligned}$$
(35)

where N is the number of training samples, \(\lambda \) is the regularization parameter, and \(\theta _j\) are the model parameters.

3.4.2 Optimization settings

  • Optimizer: Adam optimizer with learning rate set to 0.001

  • Batch size: 32

  • Early stopping mechanism: Stop training when validation set performance does not improve for 10 epochs

  • Regularization: Dropout probability set to 0.2, L2 regularization parameter \(\lambda =1e-4\)

  • Time window settings: Hourly window 24 hours, daily window 7 days, weekly window 4 weeks

3.4.3 Feature preprocessing

All numerical features are normalized to the [0,1] range through min-max normalization, and categorical features are processed through one-hot encoding. To prevent data leakage, we strictly split data in chronological order, ensuring that all commit timestamps in the test set are later than those in the training set.

4.1.3 Evaluation metrics

Given the special characteristics of JIT defect prediction tasks and practical application requirements, we constructed a comprehensive evaluation metric system that measures model performance from multiple dimensions. This metric system includes five core indicators, each with specific evaluation focuses and practical significance, providing comprehensive quantitative assessment of model performance.

Accuracy

serves as the most fundamental evaluation metric, reflecting the overall correctness of model predictions. Its calculation formula is:

$$\begin{aligned} \text {Accuracy} = \frac{TP + TN}{TP + TN + FP + FN} \end{aligned}$$
(36)

where TP represents true positives (correctly predicted as defective), TN represents true negatives (correctly predicted as non-defective), FP represents false positives (incorrectly predicted as defective), and FN represents false negatives (incorrectly predicted as non-defective). Although accuracy may have certain limitations in cases of class imbalance, it remains an important reference for measuring overall model performance.

Precision

specifically measures the model’s false alarm control capability, with the formula:

$$\begin{aligned} \text {Precision} = \frac{TP}{TP + FP} \end{aligned}$$
(37)

This metric calculates the proportion of samples predicted as defective that actually contain defects. In actual software development, excessively high false positive rates lead development teams to become overwhelmed with false alarms, reducing tool practicality. Therefore, precision is a key metric for evaluating the practical value of prediction systems.

Recall

evaluates the model’s defect detection capability, with the calculation formula:

$$\begin{aligned} \text {Recall} = \frac{TP}{TP + FN} \end{aligned}$$
(38)

This metric reflects the proportion of actual defects that are correctly identified. High recall means the model can capture more real defects, reducing missed detection risks, which is important for ensuring software quality. However, recall improvement often accompanies precision decline, requiring balance between the two.

F1-score

serves as the harmonic mean of precision and recall, with the formula:

$$\begin{aligned} \text {F1} = \frac{2 \times \text {Precision} \times \text {Recall}}{\text {Precision} + \text {Recall}} \end{aligned}$$
(39)

F1-score balances the trade-off relationship between precision and recall, providing a comprehensive evaluation standard for model performance. Compared to arithmetic mean, harmonic mean is more sensitive to smaller values, thus better reflecting balanced model performance across both metrics.

AUC (Area Under Curve)

evaluates model performance by calculating the area under the ROC curve. The ROC curve uses False Positive Rate (FPR) as the x-axis and True Positive Rate (TPR) as the y-axis:

$$\begin{aligned} \text {FPR} = \frac{FP}{FP + TN}, \quad \text {TPR} = \frac{TP}{TP + FN} \end{aligned}$$
(40)

AUC values range from 0 to 1, with larger values indicating better model performance. The AUC metric is relatively insensitive to class imbalance and can more objectively reflect comprehensive classification capability across different classification thresholds, particularly suitable for imbalanced data scenarios like JIT defect prediction.

These statistical test results not only confirm the technical effectiveness of the MSTDP method but, more importantly, provide scientific evidence for its reliability in practical applications. 4.3 Ablation study

To deeply understand the specific contributions and interaction mechanisms of each technical component in the MSTDP method, we designed systematic ablation experiments. Ablation experiments, as an important means of deep learning model analysis, can quantify the impact of each component on overall performance by progressively removing or modifying specific components of the model. This analytical approach not only helps validate the effectiveness of each technical module we designed, but more importantly, reveals the synergistic effects between different components, providing scientific basis for further optimization and improvement of the model.

4.3.1 Ablation experiment design

Our ablation experiments adopt a progressive design strategy, starting from the complete model and gradually removing different functional modules to evaluate the independent contribution of each component to model performance. The experimental design fully considers the four core technical components of the MSTDP method, ensuring comprehensive analysis of the importance of each module. To ensure comparability of experimental results, all ablation versions use the same training process, hyperparameter settings, and evaluation criteria, with the only difference being the presence or absence of specific functional modules.

Specifically, we constructed the following four ablation versions:

  1. 1.

    no_temporal: Remove the multi-scale temporal module, retaining only code, developer, and lifecycle features

  2. 2.

    no_developer: Remove the developer behavior module to evaluate the importance of developer information

  3. 3.

    no_lifecycle: Remove the project lifecycle awareness module to test the role of project stage adaptation

  4. 4.

    code_only: Retain only code features, removing all other modules as the simplest baseline

The core idea of this design strategy is to identify the unique value of each component through comparative analysis. The no_temporal version is specifically used to validate the effectiveness of our proposed multi-scale temporal analysis. This version removes the feature extraction and fusion mechanisms at hourly, daily, and weekly time scales while retaining all other functional modules. By comparing the performance differences between the complete model and this version, we can directly quantify the role of temporal information in JIT defect prediction. The no_developer version focuses on evaluating the contribution of developer behavior modeling. This version removes all personnel-related features including developer identity encoding, commit pattern analysis, and experience feature encoding, thereby isolating the impact of developer factors on prediction performance.

The no_lifecycle version aims to test the value of the project lifecycle awareness mechanism. This version removes lifecycle stage identification and expert model switching functionality, adopting a unified prediction strategy for all project stages. This design can reveal the extent to which project evolution stages affect defect patterns. The code_only version serves as the most simplified baseline model, retaining only basic code change features such as modified lines, number of files, complexity and other traditional metrics, while removing all advanced feature engineering and deep learning components. The setting of this version helps evaluate the overall advantages of our entire technical architecture relative to traditional methods.

Through this progressive ablation experiment design, we can not only evaluate the independent contribution of each component but also observe the interaction effects between components. For example, by comparing the performance differences between no_temporal and no_developer versions, we can analyze whether there are complementary or competitive relationships between temporal features and developer features. Meanwhile, comparisons between the code_only version and other versions can demonstrate the advantage level of deep feature fusion over simple feature combination.

During experiment execution, we strictly controlled all variable factors that might affect results. Each ablation version uses the same data preprocessing pipeline, feature normalization methods, and data splitting strategy. The training process adopts the same optimizer, learning rate, and regularization parameters, ensuring that performance differences entirely originate from model architecture differences rather than training process randomness. This strict experimental control provides a reliable foundation for subsequent result analysis and conclusion derivation.

4.4 Concept drift robustness experiments

The continuous evolution characteristics of software projects determine that defect introduction patterns undergo dynamic changes over time. This phenomenon, known as concept drift, poses severe challenges to the long-term stability and practical value of prediction models. Concept drift is particularly prominent in the JIT defect prediction field, as the software development process involves multiple dynamic factors such as technology stack evolution, team structure changes, and requirement adjustments. To comprehensively evaluate the robustness and adaptability of the MSTDP method when facing real software evolution environments, we designed three types of concept drift experiments to simulate different drift scenarios including natural evolution, sudden changes, and gradual changes.

4.4.1 Natural concept drift analysis

Natural concept drift experiments aim to evaluate the performance stability of the MSTDP method during the natural evolution process of real software projects. Unlike artificially constructed drift scenarios, natural drift reflects the evolution of defect patterns in software projects due to factors such as requirement changes, technology upgrades, and team adjustments during actual development processes.

We adopted sliding window technology to simulate online prediction scenarios, using 15 days as the basic evaluation window, sliding every 7 days to form overlapping time series evaluations. Within each time window, we used historical data before the window to train the model, then evaluated performance on data within the window. By calculating the standard deviation of various performance indicators across all time windows, we can quantify the stability level of the model during project natural evolution. The smaller the standard deviation, the more stable the model’s prediction performance and the stronger its robustness to concept drift. Figure 5 shows the performance stability analysis results of the MSTDP method during natural evolution across various projects, with the horizontal axis representing different software projects and the vertical axis showing standard deviation values for various performance indicators. By comparing fluctuation patterns across different projects and different indicators, we can deeply understand the adaptive characteristics of the MSTDP method in various project environments.

From the results in Fig. 5, we can observe that the model’s stability performance varies significantly across different projects, and this difference pattern reflects the adaptive capability characteristics of different technical components of the MSTDP method for various types of projects. Cloud infrastructure projects (neutron, nova) demonstrate relatively balanced and excellent stability performance, particularly with minimal fluctuation in AUC indicators, with standard deviations of only around 0.02. This stability mainly benefits from the highly structured development processes and strict code standards of cloud infrastructure projects, enabling our multi-scale temporal analysis module to effectively capture their regular development patterns. Additionally, these projects typically have comprehensive code review mechanisms and continuous integration processes, reducing sudden quality fluctuations and creating favorable conditions for stable prediction.

In contrast, the npm project shows the highest volatility in recall indicators, with a standard deviation reaching 0.2188, significantly higher than other projects. This instability mainly stems from the rapid evolution characteristics of the frontend development ecosystem: frequent technology stack updates, complex and variable dependency relationships, and rapidly iterating development patterns. As a core tool of the Node.js package management system, npm’s development process must constantly adapt to changes in the JavaScript ecosystem. This rapidly changing environment may cause our developer behavior analysis module to struggle in establishing stable prediction patterns, as developers need to frequently learn new technologies and adjust development habits.

The spring-integration project shows the largest fluctuation amplitude in precision indicators, reflecting the special challenges of enterprise-level middleware frameworks. As an enterprise application integration framework, spring-integration’s development process often involves complex business logic integration and multi-system interfacing. This complexity makes the relationship between code semantics and temporal patterns more difficult to model stably. Our semantic-temporal fusion module may require more frequent model updates and parameter adjustments when processing such projects to maintain adaptability to constantly changing integration requirements.

Deep stability analysis further reveals the fundamental causes of concept drift in different project types:

Cloud infrastructure projects (neutron, nova), due to their critical infrastructure positioning, typically adopt extremely strict development standards and quality control processes. These projects have rigorous code review processes, high test coverage, and standardized change management, making their defect introduction patterns relatively stable with minimal concept drift. Our multi-scale temporal analysis can effectively capture these regular patterns, thus achieving stable prediction performance.

Frontend tool projects (npm) face challenges from the rapid evolution of the JavaScript ecosystem, including introduction of new language features, build tool updates, and framework paradigm changes. This frequent technology stack change leads to continuous adjustments in development patterns, code styles, and quality standards, making concept drift more severe. While our developer behavior module can capture general development habits, it may need stronger self-adaptive capabilities when facing rapid technology stack changes.

Enterprise-level framework projects (spring-integration, camel) are prone to large-scale architectural refactoring and API changes during long-term maintenance, and these sudden major changes cause short-term performance fluctuations. Concept drift in these projects often exhibits phased characteristics: patterns are relatively fixed during long-term stable periods, but significant pattern changes occur during major version upgrades or architectural adjustments. Our project lifecycle awareness module can adapt to these changes to some extent, but further optimization is needed for sudden major adjustments.

These stability analysis results provide important guidance for actual deployment of the MSTDP method: for cloud infrastructure projects, relatively stable model configurations and lower update frequencies can be adopted; for frontend tool projects, more sensitive concept drift detection mechanisms and more frequent model adjustment strategies need to be designed; for enterprise-level framework projects, model update strategies should be adjusted in combination with version release plans and architectural change schedules.

4.4.2 Sudden concept drift experiments

Sudden concept drift experiments aim to evaluate the adaptability and robustness of the MSTDP method when facing major changes in software projects. In actual software development, projects frequently face sudden changes such as architectural refactoring, development paradigm shifts, and team reorganization. These changes significantly alter defect introduction patterns and feature distributions in a short time. Unlike the gradual evolution of natural concept drift, sudden drift is characterized by clear time points, widespread impact scope, and large change magnitudes.

To simulate sudden changes in real scenarios, we artificially injected concept drift at the temporal midpoint (50% position) of each dataset. Specifically, we selected feature subsets most critical for defect prediction, including code complexity, modification scale, and developer experience, and added 30% random offset to these features. This offset setting ensures significant distribution changes while avoiding excessive perturbation that would cause data to lose authenticity. Through this approach, we can observe model performance and adaptation mechanisms when facing sudden changes in a controlled environment.

Figure 6 clearly shows F1 performance changes across nine projects before and after sudden . Blue bars represent F1 scores before drift, green bars represent F1 scores after drift, and orange lines intuitively display the magnitude and direction of performance changes. From overall results, the MSTDP method demonstrates complex and interesting adaptation patterns when facing sudden concept drift, including both positive cases of performance improvement and challenging scenarios of performance decline.

Surprisingly, two out of nine projects actually showed performance improvement after sudden drift. The npm project demonstrated the most significant improvement, with F1 score dramatically increasing from 0.3697 to 0.5091, an improvement of 37.7%. This counter-intuitive result may be related to npm project’s originally low baseline performance: due to the rapid change characteristics of the frontend ecosystem, npm project’s defect patterns inherently have high instability, and our injected feature offset may have triggered expert prediction strategies in the project lifecycle awareness module that are more suitable for current data distribution.

The spring-integration project similarly shows a 7.5% performance improvement, from 0.4881 to 0.5249, indicating that our expert switching mechanism has certain self-adaptive capabilities and can automatically adjust to better prediction modes when the environment changes. However, most projects indeed experienced performance decline after sudden drift, which aligns with general negative impact expectations of concept drift on machine learning models (Xiang et al. 2023; Babüroğlu et al. 2024).

Among these, the camel project was most severely affected, with F1 score dramatically declining from 0.6658 to 0.5244, a decrease of 21.2%. This significant performance deterioration may be related to the complexity of camel project as an enterprise-level middleware framework: its complex business logic and diverse integration scenarios may make our developer behavior module and semantic-temporal fusion module difficult to quickly adapt to new patterns when core feature distributions change. The fabric project’s F1 score declined from 0.5891 to 0.5247, a decrease of 10.9%, also reflecting the vulnerability of microservice architecture projects when facing sudden changes.

Deep analysis of sudden drift adaptation mechanisms reveals several important technical characteristics of the MSTDP method:

The expert switching mechanism of the lifecycle awareness module demonstrated unexpected self-adaptive capabilities. The performance improvements observed in npm and spring-integration projects indicate that when data distribution undergoes mutation, the model can automatically activate expert sub-modules more suitable for new environments. This phenomenon suggests that our lifecycle awareness design can not only adapt to natural project evolution but also has potential for handling sudden environmental changes.

The multi-scale temporal module shows stronger robustness in projects with higher standardization levels. Cloud infrastructure projects such as neutron and nova, although still experiencing performance decline after sudden drift, have relatively small decline magnitudes of 6.1% and 4.8% respectively. This relatively stable performance benefits from strict development standards and stable temporal patterns in these projects: even when feature distributions change, underlying temporal regularities can still provide valuable information for prediction.

The cross-attention mechanism demonstrates important self-adaptive value in addressing feature distribution changes. Through analyzing detailed performance changes in each project before and after sudden drift, we found that projects with relatively smaller performance declines often have more complex and diverse feature interaction patterns. Cross-attention mechanisms can relearn and adjust weight allocations between different feature dimensions when feature distributions change, thereby partially mitigating negative impacts of sudden drift.

The results of sudden concept drift experiments provide important references for risk management in actual deployment of the MSTDP method. For projects that may face major architectural adjustments or technology stack migration, more frequent model monitoring and update mechanisms should be established; for project types that have already demonstrated good robustness, model update cycles can be appropriately extended to reduce maintenance costs. More importantly, the positive performance of the lifecycle awareness module provides new ideas and technical directions for developing self-adaptive prediction systems.

Through systematic experimental validation on 9 large-scale open-source projects, the MSTDP method demonstrates comprehensive and significant performance advantages in JIT defect prediction tasks. Comparative experimental results show that MSTDP achieves the best performance across all five evaluation metrics, improving F1 score by 0.46% and AUC by 0.52% compared to the strongest baseline JITBoost, with statistical significance testing validating the reliability of improvements. Ablation experiments deeply reveal contribution mechanisms of each technical component: multi-scale temporal features are the most critical component (F1 decline of 4.31%), developer behavior analysis provides stable contribution (decline of 1.55%), project lifecycle awareness has limited but universally effective contribution (decline of 0.87%), while synergistic effects of multi-dimensional feature fusion far exceed simple addition of individual components (code_only version F1 decline of 9.18%). Concept drift robustness experiments further confirm the practical value of MSTDP: demonstrating good stability in natural evolution, showing reasonable robustness during sudden changes, and even achieving performance improvement during gradual evolution by utilizing transition periods (mid-term F1 improvement of 2.69%), establishing a solid foundation for successful application of software defect prediction in dynamic engineering environments.

A key consideration in our results is the average precision of 61.02%. While this outperforms the baselines, it remains a moderate value. In a practical deployment, this precision rate implies that approximately 39% of the flagged commits (False Positives) would be “clean” upon review. This introduces a critical trade-off: while our model identifies more true defects (higher recall), it also demands developer attention for false alarms.

However, in many high-assurance systems, the cost of a False Negative (a missed defect that escapes to production) is often orders of magnitude higher than the cost of a False Positive (a developer spending extra minutes reviewing a clean commit). Furthermore, in a practical CI/CD pipeline, this model can be used as a pre-screening tool. For example, commits flagged by the model could be routed for mandatory peer review, while ’clean’ commits might follow a more expedited path. This workflow optimization, even with false positives, can allocate limited human review resources more efficiently to the changes that are *most likely* to be problematic. Our model’s balanced F1-score and high AUC (81.88%) suggest it provides a robust screening mechanism, and future work could focus on integrating effort-aware thresholds to allow teams to tune this precision/recall balance based on their specific quality assurance resources and risk tolerance.

4.6 Computational cost and efficiency analysis

A critical aspect of the practical viability of the MSTDP framework is its computational overhead. Given the multi-component architecture (LSTMs, cross-attention) and multi-scale processing, the framework inherently incurs more computational cost than simpler baseline models. To quantify this trade-off and evaluate its feasibility for real-world deployment, we conducted an analysis of the training and inference times. We measured the average training time (on the full training set) and the average inference time (per single commit) on our experimental hardware (NVIDIA H80 GPU).

The results are summarized in Table 5. As shown, MSTDP requires significantly more training time compared to traditional models like JITBoost but is comparable to other deep learning models like JIT-CF.

This analysis highlights the trade-off between performance and computational cost (Reviewer 2, Point 3). We observe two key findings:

  • Training Cost: The training time for MSTDP (5.1 hours) is an offline cost. While higher than traditional methods, it is a necessary investment for building a model that captures complex temporal and semantic interactions. This training would typically be performed periodically (e.g., weekly or monthly) in a production environment.

  • Inference Cost: The inference time per commit (28.5 ms) is the most critical metric for a ”Just-In-Time” scenario. This duration is negligible for a developer at the point of commit and well within the acceptable limits for real-time feedback in a CI/CD pipeline.

In conclusion, while MSTDP introduces a higher training overhead, the inference cost remains highly practical for real-world deployment. The performance gains in accuracy and AUC (e.g., 0.52% average AUC improvement over the strongest baseline) justify this one-time training cost, particularly in large-scale, high-assurance software systems where the cost of missing a defect is substantial.

5 Threats to validity

5.1 Internal validity

Internal validity threats primarily concern whether the causal relationships in the experimental process are reliable, i.e., whether the experimental results are truly brought about by our method (MSTDP) rather than other confounding factors.

Accuracy of SZZ algorithm

This study relies on the SZZ algorithm to label defect-inducing commits, which is a common practice in the JIT defect prediction field. However, the SZZ algorithm itself is not completely precise, and its labeling results may contain false positives and false negatives, thereby affecting the label quality of training data. To mitigate this threat, we selected SZZ implementations that have been widely used and validated in multiple studies, and applied them to large-scale projects with long-term, clear maintenance histories. These projects have relatively standardized commit logs and issue tracking systems, which help improve the labeling accuracy of SZZ.

Correctness of implementation code

The MSTDP model we proposed and the seven reproduced baseline models may have implementation defects in their code. To ensure fairness, for all baseline methods, we used their authors’ publicly released source code whenever possible or performed detailed reproduction following their paper descriptions. For our own MSTDP model, we conducted rigorous code review and unit testing to ensure that the implementation of each module (such as temporal feature extraction, attention fusion, etc.) is consistent with the design.

5.2 External validity

External validity threats relate to whether the conclusions of this study can be generalized to other different environments, projects, and datasets.

Representativeness of datasets

This study selected 9 large-scale, mature open-source projects. Although these projects have diversity in domain, scale, and lifecycle, they still cannot fully represent all types of software projects. For example, whether our research conclusions can be directly generalized to closed-source commercial software, small-scale projects, or software in specific domains (such as embedded systems, game development) requires further verification. We chose these well-known open-source projects because their data is publicly accessible, facilitating reproduction and comparison, but future work needs to validate the effectiveness of MSTDP in broader contexts.

Limitations of programming languages

The projects in our experiments primarily use mainstream programming languages such as Java, Python, and JavaScript. Therefore, the universality of research results for other programming languages (such as C++, C#, Go, etc.) has not been sufficiently verified. Different languages’ syntactic features and development paradigms may affect defect introduction patterns.

5.3 Construct validity

Construct validity threats concern whether the metrics and experimental design we used accurately reflect the theoretical concepts we want to study.

Limitations of evaluation metrics

We adopted a series of evaluation metrics widely recognized in academia, including accuracy, precision, recall, F1-score, and AUC. These metrics can measure model classification performance from different perspectives. However, they may not fully reflect the actual utility of a prediction model in real industrial scenarios. For example, discovering high-impact defects by reviewing a small amount of code may be far more valuable than discovering many low-impact defects by reviewing large amounts of code. Future research can incorporate evaluation using more practice-oriented metrics such as effort-aware or defect severity.

Authenticity of concept drift simulation

In concept drift robustness experiments, we simulated sudden and gradual drift by adding random offsets to features. While this method can test model adaptation capabilities in controlled environments, it remains a simplification compared to concept drift driven by complex semantic factors such as requirement changes, technical refactoring, or team adjustments in the real world. Nevertheless, this simulation provides us with a controllable, reproducible benchmark to compare the robustness of different models.

Correlation vs. Causation

A primary limitation of our construct validity is that the model, including the attention mechanisms and developer behavior analysis, is based on correlation, not causation. We do not (and cannot) claim that the learned attention weights represent true causal influence or that our developer behavior module is grounded in established behavioral psychology theories. The model learns statistical patterns from historical data (e.g., ’developers with X pattern tend to commit Y defects’). This is a common limitation in deep learning-based software engineering research. Establishing a true causal link would require different experimental designs, such as interventional studies, which are outside the scope of this paper but are a critical area for future investigation, as discussed in Section 6.5.

5.4 Conclusion validity

Conclusion validity (or statistical validity) threats relate to whether the conclusions we draw from data are reasonable and reliable.

Power of statistical tests

We used the Wilcoxon signed-rank test to verify whether the performance improvements of the MSTDP model relative to baseline methods are statistically significant. Although this is a commonly used non-parametric test method in the JIT prediction field, our comparison is based on data points from 9 projects. Future work can further strengthen the robustness of statistical conclusions by conducting experiments on more diverse projects.

Sensitivity to hyperparameters

The performance of deep learning models is influenced to some extent by hyperparameter selection. In this study, we selected a reasonable set of hyperparameters for the MSTDP model through preliminary experiments and applied unified training strategies to all models. We acknowledge that if exhaustive hyperparameter tuning were performed for each baseline model on each dataset, their performance might be further improved. However, such an approach would be extremely costly and is not commonly used in practice. Our current strategy aims to ensure a fair comparison foundation.

6 Conclusion

Software defects, as one of the most challenging problems in modern software development, have repair costs that grow exponentially with delayed discovery, seriously impacting project costs, quality, and security. This study deeply analyzed the fundamental limitations of traditional file-level defect prediction methods in terms of timeliness and precision. Addressing four key challenges in Just-in-Time (JIT) defect prediction where existing methods over-rely on static code metrics, ignore temporal dynamic characteristics, oversimplify developer behavior modeling, and lack lifecycle-aware prediction strategies, we proposed the Multi-Scale Temporal Defect Prediction framework (MSTDP). This framework successfully transformed code changes from isolated static events to dynamic context-aware comprehensive modeling by systematically integrating innovative technologies including multi-temporal scale features, deep semantic fusion, developer behavior modeling, and project lifecycle awareness, significantly improving the performance and robustness of JIT defect prediction.

6.1 Core contributions and technical breakthroughs

This study systematically addressed four key limitations in the JIT defect prediction field, achieving the following important breakthroughs in theoretical methods and technical implementation:

Systematic innovation in multi-scale temporal feature modeling

Addressing the fundamental limitation of existing methods ignoring temporal dynamic characteristics of software development, this study first proposed a systematic temporal feature extraction method covering hourly, daily, and weekly time scales. By constructing temporal feature sequences through sliding window techniques, modeling temporal dependencies using LSTM networks, and fusing information from different scales through adaptive attention mechanisms, we successfully captured development dynamics at different temporal granularities including short-term development pressure, medium-term development patterns, and long-term technical debt accumulation. Experimental results show that the introduction of temporal features improved average model performance by 6.5%, validating the critical value of systematically integrating multi-temporal scale features of software development into JIT defect prediction.

Breakthrough in deep semantic-temporal fusion architecture

The end-to-end deep learning architecture designed in this study achieved deep fusion of code semantic features and temporal patterns through cross-attention mechanisms, breaking through the technical bottleneck of simple feature concatenation in traditional methods. This architecture can learn complex nonlinear interaction relationships between ”code change content” and ”change temporal patterns,” providing new technical pathways for understanding deep semantic associations of defect introduction. Comparative experiments show that deep fusion improved F1-scores by an average of 4.2% compared to simple concatenation methods, proving the superiority of end-to-end architecture in capturing complex feature interactions.

Unified modeling of developer behavior and project evolution

The multi-dimensional developer behavior modeling method proposed in this study comprehensively characterizes developers’ personalized features including commit habits, coding styles, and professional competence through three dimensions: developer identity encoding, commit pattern analysis, and experience feature encoding, breaking through the simplified modeling of traditional methods that only consider overall experience values. Meanwhile, the project lifecycle awareness module can automatically identify project evolution stages and adopt corresponding expert prediction strategies, addressing the limitations of ”one-size-fits-all” prediction strategies. Ablation experiments confirmed that developer features and lifecycle features contribute 1.7%-2.2% and 1.1% performance improvements respectively, validating the important value of systematically incorporating dynamic evolution of developer behavior and phased changes in project lifecycle into the prediction framework.

6.2 Experimental validation and performance evaluation

Comprehensive experimental validation conducted on 9 large-scale open-source projects including Brackets, Camel, Fabric, and others verified the effectiveness and superiority of the MSTDP method:

Significant performance improvement and method superio-rity

Compared to 8 state-of-the-art baseline methods including JITBoost, FENSE, JIT-CF, TLEL, MULTI, DWA_JIT, and EALGB, MSTDP achieved significant improvements across all evaluation metrics. On average, accuracy improved to 76.89% (0.56% improvement over the highest baseline value), precision reached 61.02% (0.53% improvement), recall reached 67.82% (0.64% improvement), F1-score reached 60.93% (0.74% improvement), and AUC reached 81.88% (0.52% improvement). Performance improvements were particularly notable in cloud infrastructure projects such as neutron and nova, demonstrating good adaptability and generalization capability of our method to different types of software projects.

Strong concept drift adaptation capability validation

Concept drift experiments systematically validated the outstanding advantages of the MSTDP method in addressing long-term evolution of software projects. Under natural concept drift conditions, the model demonstrated low performance fluctuation (standard deviations generally below 0.1), proving model stability in real project evolution environments. When facing sudden concept drift, some projects even showed performance improvements (such as npm project F1-score improving from 0.3697 to 0.5091), demonstrating the self-adaptive adjustment capability of the project lifecycle awareness module. During the middle stage of gradual concept drift, model F1-scores improved by an average of 2.69%, proving that cross-attention mechanisms can effectively capture common information from new and old feature distributions when feature distributions change.

Deep insights into component contributions and architecture validation

Ablation experiments systematically quantified the contribution of each component, validating the effectiveness of the five main contributions proposed in this study. Removal of temporal features caused the largest performance decline (6.5% precision decline), further validating the core value of multi-scale temporal modeling. Removal of developer features caused 1.7%-2.2% performance decline, proving the importance of multi-dimensional developer behavior modeling. Although lifecycle features had relatively small contribution (1.1%), they demonstrated crucial self-adaptive adjustment roles in concept drift experiments. Code features, as the foundation, can maximize their utility when synergizing with other features, demonstrating the necessity of integrated neural network architecture design.

6.3 Theoretical contributions and practical value

Important theoretical contributions

This study fundamentally redefined the modeling paradigm of JIT defect prediction problems, breaking through the traditional analytical framework that treats code changes as isolated static events and establishing dynamic context-aware comprehensive modeling theory. The multi-scale temporal feature extraction method introduced systematic temporal analysis thinking to the software engineering field, revealing the impact mechanisms of different time scales including short-term development pressure, medium-term development patterns, and long-term technical debt accumulation on defect introduction. The project lifecycle awareness module provided empirical support for software evolution theory, proving that different lifecycle stages including early rapid development, middle feature refinement, and late maintenance stages indeed exhibit differentiated defect introduction patterns. The concept drift analysis framework established new evaluation benchmarks for assessing prediction model adaptation capabilities when facing long-term project evolution, providing theoretical basis for continuous effectiveness of software quality assurance.

Significant engineering practice value

The MSTDP method achieved three significant advantages in JIT defect prediction: providing more timely feedback, prediction granularity precise to specific code changes, and supporting more actionable quality assurance measures. The timely feedback mechanism enables developers to receive defect risk assessments at the moment of code commit, immediately fixing problems while memory is fresh, significantly reducing defect repair costs (early discovery costs only one-tenth of late discovery). Prediction granularity precise to specific code changes effectively addresses the defect localization difficulties in traditional file-level prediction methods, supporting targeted code review and enhanced testing strategies. The model’s strong robustness to concept drift ensures continuous effectiveness during long-term project evolution, avoiding significant prediction performance decline due to continuous software project evolution, providing reliable guarantees for long-term industrial deployment.

6.4 Systematic answers to research questions

This study systematically answered the three core research questions posed in the introduction, providing complete solutions to key challenges in the JIT defect prediction field:

RQ1 (Contribution and Fusion Mechanisms of Multi-Scale Temporal Features)

Experimental results clearly confirmed the significant improvement effect of multi-scale temporal features on JIT defect prediction performance. Hourly scale features capture immediate development context and emergency repair pressure, daily scale features reveal medium-term development patterns and work rhythms, and weekly scale features reflect long-term project trends and technical debt accumulation. Through effective fusion by adaptive attention mechanisms, features at different time scales show differentiated importance in different projects and scenarios, improving average model accuracy by 0.56% and F1-score by 0.74%. Ablation experiments further confirmed that removal of temporal features caused 6.5% precision decline, validating the critical value of multi-scale temporal modeling for improving JIT defect prediction performance and the importance of effective fusion mechanisms.

RQ2 (Role Mechanisms of Developer Behavior and Project Lifecycle)

Developer behavior modeling and project lifecycle awareness played crucial roles in defect prediction, systematically addressing the limitations of simplified developer modeling and ”one-size-fits-all” prediction strategies in traditional methods. Multi-dimensional developer behavior modeling comprehensively characterizes developers’ commit habits, coding styles, and professional competence through three dimensions: identity encoding, commit pattern analysis, and experience feature encoding, with its removal causing 1.7%-2.2% model performance decline. The project lifecycle awareness module can automatically identify different evolution stages including early rapid development, middle feature refinement, and late maintenance, and adopt corresponding expert prediction strategies, contributing 1.1% performance improvement. More importantly, the introduction of these factors significantly enhanced model adaptability to different project stages and developer characteristics, particularly the performance stability and self-adaptive adjustment capabilities demonstrated in concept drift experiments.

RQ3 (Concept Drift Robustness and Adaptation Mechanisms)

The MSTDP method demonstrated strong robustness in all three types of concept drift experiments, effectively addressing defect pattern changes caused by temporal progression and project evolution. Low performance fluctuation under natural concept drift conditions (standard deviations generally below 0.1) proved model stability in real project evolution; rapid adaptation and even performance improvement after sudden concept drift (such as npm project F1-score improvement of 37.7%) demonstrated the effectiveness of the project lifecycle awareness module; performance improvement during gradual concept drift middle stages (average F1-score improvement of 2.69%) proved that cross-attention mechanisms can effectively fuse information from new and old feature distributions. Multi-scale temporal modeling, project lifecycle awareness, and deep semantic fusion are key technical factors for achieving this robustness, collectively constituting the core mechanisms for the model to maintain stable prediction performance and adapt to changes when facing concept drift.

6.5 Future research directions and prospects

Although this study achieved important progress in the JIT defect prediction field, systematically addressing four key limitations of existing methods, there remains room for further exploration and improvement:

More fine-grained temporal modeling and adaptive mechanisms

Future work can explore minute-level or even second-level ultra-fine-grained temporal features to capture more immediate development dynamics. Meanwhile, adaptive time window selection mechanisms can be studied to dynamically adjust optimal time scale combinations based on project characteristics and development patterns, further improving the precision and adaptability of temporal modeling.

Cross-project generalization capability and transfer learning

Current MSTDP models are primarily trained and tested within single projects. Future research needs to deeply study cross-project, cross-language, and cross-domain generalization prediction capabilities. By introducing transfer learning and domain adaptation techniques, better solutions can be provided for the ”cold start” problem of new projects, expanding the application scope of the method (Zhang et al. 2023).

Real-time incremental learning and online adaptation

In actual deployment, models need to be able to learn new development patterns and defect characteristics in real-time. Future research can study deep integration of online learning algorithms with concept drift detection, achieving autonomous model evolution and continuous adaptation, further enhancing concept drift robustness (Chen et al. 2022).

Enhanced explainability and decision support

To enhance model acceptability and practicality in industrial environments, prediction result explainability needs further improvement. Through techniques such as attention weight visualization and feature importance analysis, specific causal analysis of defect risks and targeted repair suggestions can be provided to developers.

Large-scale distributed architecture and real-time deploy-ment

As software project scales continue to grow, research on MSTDP architectures suitable for large-scale distributed development environments is needed, achieving efficient model training, real-time inference, and dynamic updates to meet performance requirements of industrial-grade applications.

Exploring causal inference in defect prediction

A profound research question remains regarding the relationship between cross-attention weights and the causal strength of feature interactions. This is a significant limitation of current association-based models. Future work could employ techniques like Granger causality, Pearl’s Causal Inference (e.g., do-calculus), or interventional experiments on feature distributions to move from ”what features are correlated with defects” to ”what feature changes cause defects”. This would be a major leap forward for creating truly actionable and robust prediction tools.

Integrating behavioral psychology theories

Our current developer behavior module empirically learns feature weights from data. A promising future direction is to integrate established theories from behavioral psychology. For example, models from behavioral economics or psychology related to cognitive load, decision fatigue, or ‘flow state’ could provide a strong theoretical basis for feature engineering. This could help define a more theoretically-grounded weighting logic for developer features (e.g., how developer experience interacts with recent commit frequency, as predicted by cognitive load theory) and explore how these weights might need to be dynamically adjusted based on project context.

Dynamic and adaptive temporal windowing

Our work used fixed window sizes, but future work could explore dynamic step sizes for temporal feature extraction. For instance, instead of fixed windows, the model could learn an optimal look-back period based on project velocity (e.g., projects with a faster development pace might require shorter, more reactive windows). Techniques could be developed to quantify the information gain of different step sizes, perhaps using information theory or reinforcement learning to allow the model to select the most predictive time scale for any given commit, thus adapting to the unique development pace of different projects.

6.6 Summary

This study addressed the key challenge that software defect repair costs grow exponentially with delayed discovery time, deeply analyzed the fundamental limitations of traditional file-level defect prediction methods in terms of timeliness, and systematically solved four key problems in JIT defect prediction: over-reliance on static code metrics, ignoring temporal dynamic characteristics, simplified developer behavior modeling, and lack of lifecycle-aware prediction strategies. The proposed Multi-Scale Temporal Defect Prediction framework (MSTDP), through five main contributions including innovative multi-scale temporal feature extraction, integrated neural network architecture design, developer behavior modeling and project lifecycle awareness, and concept drift analysis framework, successfully transformed software development from traditional modeling of isolated static events to dynamic context-aware comprehensive modeling, achieving significant advantages in timely feedback, precise localization, and actionable quality assurance for JIT defect prediction.

Large-scale experimental validation proved the effectiveness and superiority of this method, not only comprehensively surpassing existing state-of-the-art methods in performance metrics but also demonstrating outstanding robustness in concept drift adaptation capabilities, making important contributions to the development of software quality assurance technology. As software system complexity continues to grow and development patterns continuously evolve, the theoretical framework, technical methods, and analytical tools provided by this study will lay important foundations for building more intelligent, adaptive, and precise software quality assurance systems, promoting the transformation of JIT defect prediction technology from laboratory research to industrial applications, ultimately achieving the goals of early discovery, timely repair, and significant reduction in software defect repair costs.
